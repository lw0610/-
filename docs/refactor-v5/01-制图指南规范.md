# 01 制图指南规范

## 1. 定位

制图指南替代流程包，是给编排智能体看的“专门知识”：这类地图要做什么、需要什么数据、每个图层怎么处理、版面有什么要求、怎样算完成。它**不规定**由哪个角色做、按什么表单输入、按哪几步固定执行——这些由编排智能体在计划中决定（`02`）。

| 指南里写 | 指南里不写 |
|---|---|
| 适用任务、需要明确的信息及默认值 | 负责角色、`负责` 字段、角色名 |
| 需要的数据：是什么、范围、字段要求、可以从哪里来 | 输入表单类型（文件 / 文件夹 / 图层选择器） |
| 图层处理表：每个图层的数据、处理、样式、标注、顺序、图例 | 步骤编号、执行条件、失败策略 |
| 制作要点：按阶段写方法、约束与需要的能力 | 工具名与参数细节 |
| 版面要求、产出与检查、使用的资源、注意事项 | 数据来源编号（来源由数据服务选择） |

## 2. 存放与文件

- 位置沿用流程包目录（README §9 第 2 项）：内置 `autocarto/flows/system/<编号>/`，用户 `<AUTOCARTO_HOME>/flows/<编号>/`。复用现有存储、导入导出、版本、`flow.lock` 与资源解析（`internal/flow/store.go`、`export.go`、`import.go`、`lock.go`、`internal/resource/**`）。
- 主文件 `GUIDE.md`。目录中只有 `FLOW.md` 时视为旧流程，按 §7 转换。
- 资源仍放在 `resources/`，写法与解析不变。

```text
marching-route/
├── GUIDE.md
├── flow.lock
└── resources/
    ├── data/中国底图.csv
    ├── styles/路线样式-红蓝对比.csv
    └── symbols/军标/ …
```

## 3. GUIDE.md 格式

### 3.1 头部

```markdown
---
编号: marching-route
名称: 行军路线图
说明: 根据史料或已整理的路线数据集，制作带路线、专题符号、图文标注和完整版面的行军路线专题图。适用于“行军路线”“战役路线”“长征路线图”等请求。
版本: 4.0.0
标签: 专题图、路线、历史
---
```

`说明` 是编排智能体判断是否使用本指南的依据（进入技能索引），写清楚“什么请求适用”，不超过 300 字。

### 3.2 章节

| 章节 | 必需 | 内容 | 解析方式 |
|---|---|---|---|
| `## 适用任务` | 是 | 适用与不适用的情况；典型说法 | 原文 |
| `## 需要明确的信息` | 否 | 每项一行：名称（属性）：说明；属性可写 `默认 X`、`可选值：A、B`、`必须` | 结构化（复用输入属性解析） |
| `## 数据` | 是（无数据的指南写“无”） | 数据表（§3.3） | 结构化 |
| `## 图层处理` | 有地图产出时是 | 图层处理表（§3.4） | 结构化 |
| `## 制作要点` | 是 | 按阶段写方法；可用三级标题分阶段；每个阶段可写“需要的能力：A、B”和“本阶段产出：…” | 原文 + 引用检查 |
| `## 版面要求` | 有版面时是 | 版式、元素、文字规则 | 原文 + 引用检查 |
| `## 产出与检查` | 是 | 产出声明（沿用现有写法，如 `「成果 PDF」（文件，pdf）`）与检查项（§3.5） | 结构化 |
| `## 使用的资源` | 否 | 沿用现有资源声明写法 | 结构化（现有解析器） |
| `## 注意事项` | 否 | 必须遵守的规则 | 原文 |

### 3.3 数据表

```markdown
## 数据

| 数据 | 内容 | 范围 | 字段 | 可以来自 | 说明 |
|---|---|---|---|---|---|
| 史料原文 | 对话原文 | — | — | 对话 | 用户消息中的史料；与「路线数据集」至少有一项 |
| 路线数据集 | 数据集（路线格式） | — | — | 用户、产生：路线知识抽取 | 用户已提供且未要求重新抽取时直接使用 |
| 中国底图 | 清单「中国底图」 | 「路线数据集」外扩 20% | 见清单 | 用户、获取 | 8 个底图图层；用户文件夹缺项时只获取缺项 |
```

| 列 | 写法 | 说明 |
|---|---|---|
| 数据 | 名称 | 指南内唯一，正文中以 `「名称」` 引用 |
| 内容 | `类别：<类别名或别名>`、`清单「<数据清单资源>」`、`数据集（路线格式）`、`对话原文`、`文本` | 类别来自 v4 类别词表（`autocarto/tools/system/data-acquisition/assets/categories.yaml`） |
| 范围 | `全国`、`「信息或数据名」`、`「数据名」外扩 N%`、`—` | 与 v4 方案 `docs/refactor-v4/02-数据需求与数据源规范.md` §3.4 相同的范围写法 |
| 字段 | `NAME=name; CODE=code` 或“见清单” | 与 v4 清单“字段”列写法相同 |
| 可以来自 | 顿号分隔，按优先顺序：`对话`、`用户`、`工程`、`获取`、`产生：<能力>` | 只是“允许的来路”，具体来源由数据服务与编排智能体决定 |
| 说明 | 原文 | 取舍条件、注意事项 |

### 3.4 图层处理表

```markdown
## 图层处理

| 图层 | 数据 | 处理 | 样式 | 标注 | 顺序 | 图例 |
|---|---|---|---|---|---|---|
| 省域 | 「中国底图」省域 | 直接加载 | 「国标底图样式」 | NAME | 底 | 否 |
| 路线 | 「路线数据集」 | 按主线、分支、汇入绘制，保留方向 | 「路线样式-红蓝对比」 | 路线名称 | 上 | 行军路线 |
```

| 列 | 说明 |
|---|---|
| 图层 | 成图中的图层名 |
| 数据 | 引用数据表中的数据，清单数据可写到行（`「中国底图」省域`） |
| 处理 | 加载、裁剪、筛选、派生、绘制等要求（业务语言，不写工具参数） |
| 样式 | 引用资源（样式集、样式、路线样式、符号）或写规则 |
| 标注 | 字段名或规则；“无”表示不标注 |
| 顺序 | `顶`、`上`、`中`、`下`、`底`，或数字（1 在最上） |
| 图例 | `否`、`是`，或图例中的显示名称 |

图层处理表同时供三方使用：编排智能体据此安排步骤；执行图层工作的角色在步骤消息中收到相关行；最终检查据此核对图层是否齐全（§3.5）。

### 3.5 产出与检查

```markdown
## 产出与检查

- 「成果 PDF」（文件，pdf）：以地图标题命名
- 「版面」（版面）
- 检查：版面元素包含 主图、标题、网格、装饰边框、综述、图例、比例尺、指北针
- 检查：图层处理表中的图层都已在工程中
- 检查：说明栏包含「数据来源说明」
- 交付说明：成果路径；使用的底图图层；路线数量、专题点数量；图文标注成功与失败项
```

- 产出声明沿用现有类型（文件、图层、版面、文本、数据集、审查结果），执行器按类型核验（复用 `internal/flowrun/verify_outputs.go`）。
- `检查：` 行支持三种可自动核验的写法：`版面元素包含 …`、`图层处理表中的图层都已在工程中`、`说明栏包含「…」`；其他写法作为人工或读图审查的检查项。
- `交付说明：` 供最终汇总。

### 3.6 引用

正文中的 `「名称」` 可以指向：需要明确的信息、数据、图层、资源、产出。解析时检查能否对上，对不上给警告（不阻止使用）。

## 4. 解析与诊断

新建 `internal/flow/guide.go`（或 `internal/guide/`，由 K10 决定，见 `06`）：

```go
type GuideDoc struct {
	Meta        FlowMetadata   // 复用
	Applicable  string
	Info        []InfoDoc      // 需要明确的信息（复用输入属性解析，得到默认值、可选值、是否必须）
	Data        []DataItemDoc  // 数据表
	Layers      []LayerSpecDoc // 图层处理表
	Method      []DocSection   // 制作要点（按三级标题分段，含“需要的能力”“本阶段产出”）
	Layout      string         // 版面要求
	Outputs     []OutputDeclaration // 复用
	Checks      []CheckDoc
	Resources   []ResourceDoc  // 复用
	Rules       []string
	Diagnostics []Diagnostic
}
```

| 诊断码 | 级别 | 条件 |
|---|---|---|
| `GUIDE_SECTION_MISSING` | 错误 | 缺少必需章节 |
| `GUIDE_ROLE_FIELD` | 错误 | 出现 `负责`、`执行者`、`## 参与角色` |
| `GUIDE_ROLE_NAME` | 警告 | 正文出现默认方案中的角色显示名（如“数据工程专家”） |
| `GUIDE_DATA_DUPLICATE` | 错误 | 数据名重复 |
| `GUIDE_DATA_CONTENT_INVALID` | 错误 | 内容列无法识别；类别不在词表；清单资源不存在 |
| `GUIDE_DATA_ORIGIN_INVALID` | 错误 | “可以来自”含未知写法；`产生：` 后的能力不存在 |
| `GUIDE_LAYER_REF_UNKNOWN` | 警告 | 图层表引用了不存在的数据、清单行或资源 |
| `GUIDE_CAPABILITY_UNKNOWN` | 警告 | “需要的能力”中的工具包不存在 |
| `GUIDE_TOOL_DETAIL` | 提示 | 制作要点像工具参数说明（复用现有 `stepHasToolDetail` 判断） |
| `GUIDE_REF_UNRESOLVED` | 警告 | `「名称」` 对不上任何对象 |
| 资源诊断 | 沿用 | 资源解析器现有诊断（不存在、歧义、锁定变化等） |

内置指南必须零错误、零警告（K51 守卫）。

## 5. 加载到智能体

- **指南索引**：新建技能后端 `GuideBackend`，实现 eino 技能中间件的 `skill.Backend`（`List` 返回每份指南的名称与说明，`Get` 返回指南全文）。与工具包技能后端一起用 `NewMultiSkillBackend` 合并（`internal/deepagent/subagents/skill_loader.go`），只挂给编排智能体（Build 与 Plan 模式）。
- **全文内容**：`Get` 返回的正文包含 GUIDE.md 原文，以及系统附加的“资源摘要”（每个资源的名称、类型、条目数与问题）和“数据可用性摘要”（数据表中每项按 `data_find` 预判的可用来源，不联网）。
- **手动指定**：用户在输入框用 `/` 选择指南（`04` §1）时，消息携带 `guide_id`；编排提示要求此时直接读取该指南，不再自行匹配。
- **专家拿到什么**：执行某一步的角色不读整份指南，只在步骤消息中收到计划写明的指南摘录（相关制作要点、图层处理表的相关行、注意事项、资源摘要），由执行器按计划生成（`02` §7.4）。
- **停用**：指南库中可停用某份指南，停用的不进入索引。

## 6. 资源作用域

计划引用指南时记录指南编号、版本与 `flow.lock` 摘要。执行器运行每一步时设置资源作用域（复用 `resource.WithScope`，`FlowID`、`FlowDir`、`Lock`、已链接资源），工具中以资源名称引用的样式、版式、符号照常解析。指南在计划生成后被修改时，执行前提示“指南已更新，按新版本重新生成计划或继续使用旧版本”。

## 7. 旧流程的转换

### 7.1 规则

| FLOW.md | GUIDE.md |
|---|---|
| 头部 | 头部，版本主号加一 |
| `## 适用场景` | `## 适用任务` |
| `## 参与角色` | 删除；各角色“工具包”写入对应阶段的“需要的能力” |
| `## 需要准备` 中文本、数字、是/否、选项类输入 | `## 需要明确的信息`（保留默认值、可选值） |
| `## 需要准备` 中文件、文件夹、图层、对话原文类输入 | `## 数据` 表的行（“可以来自”按原写法推出：对话原文 → `对话`；文件/文件夹 → `用户`；图层 → `工程`） |
| `## 数据需求` | 合并进数据表的“内容”“范围”“字段”，“可以来自”加 `获取` |
| `## 使用的资源` | 原样保留 |
| `## 步骤` | `## 制作要点`：每步一个三级标题，保留做法原文；删除“负责”；“条件”改写为“仅在……时需要”；完成标准中的中间产出写为“本阶段产出”；最终产出移入 `## 产出与检查` |
| “失败时” | 只保留“停止”类要求，写入注意事项；其余删除（失败处理由执行器与编排智能体负责） |
| `## 必须遵守` | `## 注意事项` |
| `## 交付` | `## 产出与检查` 的“交付说明” |

### 7.2 执行

- **内置指南**：四份内置流程由 K12 按 `07` 的范本手工改写，不用转换器。
- **用户流程**：启动时对只有 `FLOW.md` 的用户目录运行转换器，生成 `GUIDE.md`，原文件改名为 `FLOW.md.bak`（不删除）；在指南库标记“已自动转换，请检查”，并列出需要人工处理的项（如未能改写的条件）。转换可重复执行，已有 `GUIDE.md` 时跳过。
- **导入**：导入只含 `FLOW.md` 的包时同样转换，并在导入结果中显示转换报告。

## 8. 编写要求（写入新的编写指南）

1. 用业务语言写“做什么、用什么数据、图层怎么处理、怎样算完成”，不写角色、不写工具参数。
2. 数据表写清内容与范围；能自动获取的写 `获取`，必须用户提供的不写。
3. 图层处理表覆盖成图中的每一个图层；样式、标注字段与资源保持一致。
4. 需要明确的信息尽量给默认值；只有确实无法推断、又影响结果的才写 `必须`。
5. 制作要点按阶段写；可选阶段写清何时需要（例如“仅在用户要求质量审查时需要”）。
6. 产出与检查写成可核验的形式。
