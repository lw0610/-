## 1. 结论

**一句话**：制图任务是开放式的，应由智能体理解需求、制定计划；系统负责把计划可靠地执行、核验和记录。流程包不再规定“谁来做、按什么表单输入、按哪几步固定执行”，只说明“要做什么、需要什么数据、图层怎么处理、怎样算完成”。所有取数方式收拢为一个数据服务，由一个固定的决策顺序和一个系统级数据获取智能体负责。

| 现在 | 改为 |
|---|---|
| 流程包写死负责角色、输入表单、步骤、条件、失败策略 | **制图指南**：适用任务、需要明确的信息、数据、图层处理表、制作要点、版面要求、产出与检查 |
| 选流程后填表：每个输入选来源方式、填类型、展开获取计划、处理校验 | 用一句话描述任务；需要时补充附件、`@图层`、`/指南`；智能体只问缺少且无法推断的信息 |
| 两套规划与执行：对话里智能体自由委派；流程里确定性控制器按 FLOW.md 执行 | 一套：编排智能体出**制图计划**（可见、可改），运行时**计划执行器**按计划执行、核验、记录 |
| 流程按角色名绑定方案（v4 加了角色位、映射、补齐策略来缓解） | 计划的每一步只写需要的**能力**（工具包），运行时按能力挑选方案角色，缺少时临时补齐；指南里不出现角色 |
| 十几种取数方式分散在三个角色和多份工具包说明里；确定性规划器只在流程里可用 | **统一数据服务**：`data_find`（查候选、给理由）、`data_get`（按来源获取并记录来源）；数据获取由**系统数据获取智能体**统一负责 |

### 2.2 为什么“不知道智能体会用哪一种”

1. **两套决策互不相通**：确定性的获取规划器（`internal/acquire/planner.go` 的 `Plan` 需要 `*flow.FlowPlan`）只在流程里通过 `{"$acquire": true}` / `{"$fill": …}` 生效（`internal/websocket/flow_acquisition_policy.go`）；对话里智能体用不到它。
2. **对话中的选择靠阅读多份说明**：默认方案的数据工程专家挂了 12 个工具包（`defaults/agent_configs/default/agent.yaml:49`，含浏览器、GEE、OSM、行政区、地理编码），脚本专家、空间分析专家也各有一部分。每份工具包说明只讲自己的工具，各自写“优先用专用工具”“必要时用浏览器”，没有一个统一的“先查什么、再用什么”的规则，也没有给用户看的“数据计划”。
3. **来源记录只在流程里完整**：对话中用网页、浏览器取得的数据，没有进入数据仓，也不一定有统一的来源记录。

### 2.3 为什么流程显得混乱

1. **一个文件同时规定了三类事情**：做什么（领域知识）、谁来做（`## 参与角色`、每步“负责”）、怎么执行（步骤编号、条件、失败策略、带类型的输入）。真正属于流程的只有第一类。
2. **为了弥补僵硬又加了配置**：v4 增加了角色位、角色对应、补齐策略、输入来源方式、获取计划面板、数据需求页签、流程策略设置。每一项都合理，叠加起来就是用户要点很多东西（`FlowComposer.tsx` 378 行、`AcquisitionPlanPanel.tsx` 202 行、`RoleMappingPanel.tsx`、`DataRequirementsPanel.tsx`、`FlowPolicySettings.tsx`）。
3. **两套执行引擎**：流程有 `internal/flow`（约 7500 行）+ `internal/flowrun`（约 3800 行）的编译与控制器；对话有编排智能体加子智能体委派；Plan 模式还是另一个独立配置的规划智能体，与执行不衔接。

**根因**：把开放式的制图任务做成了“固定工作流 + 表单”，再不断加配置来找回灵活性。

## 3. 业界做法与借鉴

| 做法 | 出处 | 本方案怎么借鉴 |
|---|---|---|
| “工作流”适合步骤固定的任务，“智能体”适合步骤无法预先确定的开放任务；从最简单的方案开始；智能体每一步要从环境取得真实结果，并在检查点请人确认；工具设计要让错误难以发生 | Anthropic《Building effective agents》 | 制图整体交给智能体规划；只在固定子过程（路线知识抽取、数据获取管线）保留确定性工作流；执行器逐步核验；计划确认是检查点 |
| 把专门知识打包为“技能”，平时只加载名称和简介，需要时才读全文 | Anthropic Agent Skills；本项目已用的 eino 技能中间件（`internal/deepagent/subagents/skill_loader.go`）；GeoCode 的技能 | 流程包改为“制图指南”，以技能方式按需加载 |

## 4. 目标架构

### 4.1 五层

```text
① 指南层（做什么）      制图指南：适用任务 / 需要明确的信息 / 数据 / 图层处理表 / 制作要点 / 版面要求 / 产出与检查 / 资源
        │ 按需加载
② 计划层（智能体规划）   编排智能体：理解需求 → 澄清缺少的信息 → data_find 查数据来源 → 生成“制图计划”（可见、可改）
        │ 用户确认（或按策略自动开始）
③ 执行层（系统保证）     计划执行器：按能力选角色（缺少时临时补齐）→ 逐步执行 → 回执与产出核验 → 记录 run.json → 失败时交回编排智能体修订
        │
④ 能力层                QGIS 工具、模板与样式、统一数据服务（data_find / data_get + 数据仓）、系统专家（数据获取、路线知识抽取）
        │
⑤ 界面层                对话（附件、@图层、/指南）、问题卡、计划卡、进度卡、会话工作区（文件 / 任务 / 过程）、指南库
```

### 4.2 一次任务的样子

1. 用户：“根据这段史料做一张行军路线图，A1 横向。”（粘贴史料；可拖入自己的底图文件夹）
2. 编排智能体加载“行军路线图”指南；从对话与环境确定已知信息（纸张 A1 横向、史料在本条消息、工程里没有底图）；只问一个问题（如“底图使用您的文件夹还是自动获取？”，以问题卡给出选项；用户已拖入文件夹时不问）。
3. 编排智能体调用 `data_find` 为底图 8 个图层查来源，生成计划卡：数据（每项来源与状态）、步骤（抽取路线知识 → 获取并加载底图 → 底图符号化 → 绘制路线与专题点 → 版面 → 图文标注 → 导出）、产出、采用的默认值。
4. 用户点“开始”（或说“开始”）。计划执行器逐步执行，进度显示在对话与“任务”页签，产出出现在“文件”页签。
5. 某步失败时，执行器暂停并把失败原因交给编排智能体；编排智能体修订剩余计划（或请用户决定），确认后继续。
6. 完成后核验产出与检查项，交付成果、来源说明与遗留问题。

### 4.3 什么交给智能体，什么由系统保证

| 交给智能体 | 由系统确定性保证 |
|---|---|
| 判断用哪份指南、理解用户的数据与要求 | 指南与资源的解析、版本与锁定（复用资源解析器、`flow.lock`） |
| 决定要问哪些问题、采用哪些默认值 | 计划结构校验（引用、能力、产出类型、检查项） |
| 制定与修订计划步骤 | 按能力选角色与临时补齐（复用 v4 F11/F12） |
| 在候选来源之间做取舍（必须从 `data_find` 结果中选） | 候选来源的筛选与排序、合规排除、获取管线、数据仓、来源记录（复用 v4 数据获取引擎） |
| 每一步的具体操作与工具参数 | 回执解析与产出核验、运行记录与恢复、会话文件登记（复用 `internal/flowrun`、`internal/sessionfiles`） |

### 4.4 与智能体方案的关系

- 方案中的角色仍是“专家”：有自己的提示词、模型和工具包。指南里**不出现角色名**。
- 计划的每一步写“需要的能力”（工具包显示名或编号）。执行器选择拥有这些能力的方案角色；没有时按 v4 的临时补齐机制合成角色（受限工具包仍不补齐）。
- 两个**系统专家**不依赖方案：数据获取智能体（`03`）、路线知识抽取（复用现有执行器）。用户方案缺这两类角色时照样可用。
- 方案中的“启用的流程”、角色对应、流程策略不再需要（`05`）。

## 6. 整体验收标准

1. **Y1 一句话起步**：在对话中描述任务即可开始；不选流程、不填表单。行军路线图、统计专题图、交通线路图、通用数据成图四类任务均能匹配到指南（`/指南` 可手动指定）。
2. **Y2 问得少**：已在消息、附件、工程或默认值中确定的信息不再询问；需要询问时一次问完，以问题卡给出选项。
3. **Y3 计划可见**：涉及指南、数据获取或三步以上的任务先出计划卡，列出数据来源、步骤、产出与采用的默认值；用户可以用一句话修改计划。
4. **Y4 指南与方案解耦**：四个内置指南不含任何角色名；在 Zttzt 结构方案、默认方案、只含主角色的方案中都能执行（缺少的能力临时补齐，受限工具包除外）。
5. **Y5 取数只有一条路**：所有取数都经过 `data_find` 选择来源；只有数据获取智能体（及计划执行器）能获取数据；网页、浏览器、自定义 OSM 查询只作为兜底，并同样进入数据仓与来源记录。
6. **Y6 选择有据**：每项数据的来源都能说明“为什么选它、没选其他的原因”（来自 `data_find` 的理由与排除原因）。
7. **Y7 可靠执行**：每步都有回执与产出核验；失败时编排智能体修订计划或请用户决定，最多三次修订后停止并报告。
8. **Y8 可恢复、可追溯**：中断后可恢复；`run.json` 记录计划版本、每步结果、数据来源；会话文件区列出全部产出。
9. **Y9 界面精简**：流程表单、角色对应、流程策略、方案中的“启用的流程”从界面移除；设置中只保留模型、扩展服务、数据获取、计划确认。
10. **Y10 不退化**：v3 五项真实 QGIS 离线验收的制图结果（以行军路线图为主）在新架构下复现；v4 的数据获取离线验收（自动获取 8 层、补齐 8 层）在新架构下通过。
11. **Y11 门禁**：`./build.sh check` 通过。

## 7. 全局执行约束

在 v2、v3、v4 `README.md` §6 全部仍然适用的约束基础上：

1. **开工前确认工作区**：v4 的实施结果尚未提交。K00 先由用户确认提交（或明确授权执行智能体提交）到 `refactor/v4`，再从它建 `refactor/v5`；执行智能体不得丢弃或覆盖未提交的改动。
2. **请求路径不调模型、不联网**：指南解析、计划校验、`data_find`、表单与界面接口都是本地确定性计算；联网只发生在执行中的获取任务里。
3. **指南不写角色、不写工具参数**：指南中出现角色名、`负责`字段或工具参数细节时给出诊断；内置指南必须零诊断。
4. **只有数据服务取数**：除数据获取智能体与计划执行器外，任何角色默认不挂取数类工具包（`03` §6）；取得的数据必须进入数据仓或会话目录并有来源记录。
5. **计划必须可核验**：计划中每一步的产出声明都使用已有的产出类型（文件、图层、版面、文本、数据集、审查结果）；执行器只按核验结果推进。
6. **复用优先**：v4 已实现并通过测试的部件（数据获取引擎、数据源目录、数据仓、OSM 工具链、会话文件区、角色临时补齐、回执与核验、运行记录与恢复）只改接口、不重写；`05` 列出的删除项才删除。
7. **旧数据不丢**：用户自建流程在启动时转换为指南，原 `FLOW.md` 备份保留；旧 `run.json` 只读可查。
8. **验证记录写在 `docs/refactor-v5/evidence/`**，提交信息以任务号开头（例如 `K22: 计划执行器复用流程控制器`），在 `refactor/v5` 分支提交，不推送、不合并。

## 8. 交给执行智能体时的提示词

```text
你是本仓库的执行智能体，请完成任务 Kxx。
1. 先阅读 docs/refactor-v5/README.md（特别是 §4、§7），再阅读 docs/refactor-v5/06-任务卡.md 中该任务的任务卡与卡中“必读”列出的文档；涉及删除或复用的，必须读 docs/refactor-v5/05-迁移与清理清单.md 中对应行。
2. 只修改任务卡“涉及范围”中的文件；开工前确认 06 文件归属表中，你要改的文件没有被正在进行的其他任务占用；确需修改范围外文件时，在验证记录中说明原因。
3. 完成后运行任务卡中的测试命令，按 docs/refactor-v3/evidence/README.md 的格式写 docs/refactor-v5/evidence/<任务号>.md，并在 refactor/v5 分支提交（提交信息以任务号开头，不推送）。
4. 本方案与代码现状不一致时，以代码为准实现任务目标，并在验证记录中写明差异。
5. 不要开始其他任务。
```

## 10. 术语

| 术语 | 含义 |
|---|---|
| 制图指南 | 替代流程包；说明要做什么、需要什么数据、图层怎么处理、怎样算完成；不规定角色与固定步骤（`01`） |
| 制图计划 | 编排智能体按指南与本次情况生成的结构化计划：已知信息、假设、数据、步骤、产出、检查（`02` §4） |
| 计划执行器 | 运行时按计划逐步执行、核验、记录的组件，由现有流程控制器改造而来（`02` §7） |
| 能力 | 工具包；计划步骤按能力选角色 |
| 系统专家 | 不依赖用户方案、系统内置的专用智能体：数据获取智能体、路线知识抽取 |
| 统一数据服务 | `data_find`（查候选来源）与 `data_get`（获取并记录来源），底层复用 v4 获取引擎（`03`） |
| 数据源手册 | 数据源目录中每个来源的说明：适合什么、不适合什么、覆盖、比例尺、字段、注意事项（借鉴 LLM-Find） |
