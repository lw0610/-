# 02 计划与执行规范

## 1. 原则

1. **智能体规划，系统执行**：编排智能体根据指南、对话与环境生成“制图计划”；计划执行器按计划逐步执行、核验、记录，不自行增删步骤。
2. **计划可见、可改**：计划以卡片展示；用户用一句话即可修改（“铁路用我自己的数据”“不要质量审查”），编排智能体据此修订。
3. **每一步都有真实结果**：每步结束读取回执、核验声明的产出；不凭模型自述推进（Anthropic “从环境取得真实结果”的要求）。
4. **失败交回规划者**：执行器不自作主张绕过失败，把失败交给编排智能体修订计划或请用户决定（Magentic-One 的“卡住时重新规划”）。

## 2. 何时出计划

| 情况 | 做法 |
|---|---|
| 匹配到指南（或用户用 `/` 指定） | 出计划 |
| 没有指南，但需要获取数据、或预计三步以上 | 出计划（`guide` 为空） |
| 简单操作（加载一个文件、改一个样式、查看图层信息） | 不出计划，编排智能体直接委派（现有方式） |

## 3. 澄清问题

- 先从对话原文、附件、`@图层`、工程状态、会话已有文件、数据记忆（`03` §7）、指南默认值中确定信息；能确定的不问。
- 只问“影响结果且无法推断、没有默认值”的信息；一次问完。
- 用现有 `hitl_request` 发问，带选项时以问题卡显示（`04` §2）；用户也可以直接打字回答。
- 采用了默认值或推断值的，写进计划的“已知信息”或“假设”，在计划卡中显示，用户可改。

## 4. 制图计划

### 4.1 结构（`carto-plan/v1`）

```json
{
  "api_version": "carto-plan/v1",
  "plan_id": "cp-20261027-101500-ab12",
  "version": 1,
  "goal": "根据用户提供的史料制作 A1 横向行军路线图",
  "guide": {"id": "marching-route", "version": "4.0.0"},
  "facts": [
    {"name": "纸张", "value": "A1 横向", "from": "用户消息"},
    {"name": "地图标题", "value": "中央红军长征路线图", "from": "推断"}
  ],
  "assumptions": [
    {"text": "用户未要求质量审查，按默认不执行", "impact": "low"}
  ],
  "data": [
    {"id": "d1", "name": "史料原文", "from": "conversation"},
    {"id": "d2", "name": "路线数据集", "from": "step", "step": "s1"},
    {"id": "d3", "name": "中国底图", "from": "acquire", "find_id": "df-7c21", "choice": "auto"}
  ],
  "steps": [
    {
      "id": "s1", "title": "抽取路线知识",
      "capabilities": ["路线知识抽取"],
      "uses": ["d1"],
      "guide_sections": ["路线知识"],
      "instructions": "从史料抽取路线数据集，按指南的路线知识要求区分主体、路径顺序与注记。",
      "outputs": [{"label": "路线数据集", "type": "dataset", "format": "route_dataset"}]
    },
    {"id": "s2", "title": "获取底图", "kind": "acquire", "data": ["d3"], "depends_on": ["s1"]},
    {
      "id": "s3", "title": "加载并符号化底图",
      "capabilities": ["数据加载与导出", "符号与标注"],
      "uses": ["d3"], "layers": ["省域", "县级城市驻地", "铁路", "公路", "国道", "地区界线", "河流线", "河流面"],
      "guide_sections": ["底图"],
      "instructions": "按清单加载 8 个底图图层并按国标底图样式符号化与标注。",
      "outputs": [{"label": "底图图层", "type": "layers"}]
    }
  ],
  "deliverables": [{"label": "成果 PDF", "type": "file", "format": "pdf"}],
  "checks": ["版面元素包含 主图、标题、网格、装饰边框、综述、图例、比例尺、指北针", "图层处理表中的图层都已在工程中"]
}
```

| 字段 | 说明 |
|---|---|
| `facts` | 已确定的信息及其来源（用户消息、附件、工程、默认值、推断） |
| `assumptions` | 影响结果的假设，`impact` 为 `low` / `high` |
| `data[].from` | `conversation`（对话原文）、`user`（`path`）、`project`（`layer`）、`session`（本会话已有文件 `file_id`）、`step`（由某步产生）、`acquire`（经数据服务获取，必须带 `find_id`） |
| `data[].choice` | 仅 `acquire`：`auto`（按 `data_find` 排序第一）或某个候选编号；清单数据可按行写 `{"行名": "候选编号"}` |
| `steps[].kind` | 省略为普通步骤；`acquire` 为数据获取步骤（由系统执行，不需要能力）；`confirm` 为请用户确认 |
| `steps[].capabilities` | 需要的工具包（显示名或编号），或系统专家名（`路线知识抽取`） |
| `steps[].role_hint` | 可选：编排智能体建议的方案角色编号，执行器优先考虑 |
| `steps[].uses` / `layers` / `guide_sections` | 本步使用的数据、处理的图层（图层处理表行）、需要附上的指南章节 |
| `steps[].outputs` | 产出声明，类型沿用现有类型 |
| `deliverables`、`checks` | 最终产出与检查（默认取指南的“产出与检查”） |

### 4.2 校验（确定性，`internal/plan/validate.go`，新建）

| 检查 | 不通过时 |
|---|---|
| 结构与字段类型 | `PLAN_SCHEMA_INVALID` |
| 编号唯一；`depends_on`、`uses`、`step` 只引用已存在且更早的步骤或数据 | `PLAN_REF_INVALID` |
| 能力存在（工具包或系统专家） | `PLAN_CAPABILITY_UNKNOWN` |
| 产出类型合法；最终产出由某步声明 | `PLAN_OUTPUT_INVALID` |
| `acquire` 数据带有效的 `find_id`，`choice` 是该次查询的候选之一（防止编造来源） | `PLAN_SOURCE_NOT_FROM_FIND` |
| `user` 路径存在；`project` 图层存在；`session` 文件在会话文件索引中 | `PLAN_DATA_MISSING` |
| `layers` 都在指南图层处理表中；`guide_sections` 都存在 | `PLAN_GUIDE_REF_INVALID`（警告） |
| 指南中“可以来自”不允许的来路（例如指南要求用户提供，却写了 `acquire`） | `PLAN_ORIGIN_NOT_ALLOWED` |

校验失败时 `plan_propose` 返回诊断给编排智能体修正，不显示给用户。

## 5. 计划工具

| 工具 | 谁用 | 作用 |
|---|---|---|
| `plan_propose` | 编排智能体 | 提交计划；通过校验后存入 `<会话目录>/plans/<plan_id>.json`，在对话中显示计划卡；按 §6 判断是否需要确认；需要确认时结束本轮等待用户，否则本轮结束后自动开始执行 |
| `plan_revise` | 编排智能体 | 修订尚未执行的部分（步骤、数据、已知信息），版本加一；已完成的步骤与产出保留；运行中修订在执行器暂停时生效 |
| `data_find` | 编排智能体、数据获取智能体 | 查候选来源（`03` §3） |
| `hitl_request` | 编排智能体 | 澄清问题与关键确认（现有工具） |

`flow_start`、`flow_preview` 两个工具删除（`05`）。

## 6. 确认策略

设置“计划确认”（README §9 第 1 项）：

| 值 | 规则 |
|---|---|
| `when_needed`（默认） | 有以下任一情况时需要用户点“开始”：数据需联网获取；有 `impact=high` 的假设；包含读图审查；步骤超过 10 个。其余自动开始，计划卡照样显示 |
| `always` | 每次都确认 |
| `never` | 从不确认（计划卡仍显示，可随时“停止”） |

判断由运行时完成，不交给模型。

## 7. 计划执行器

### 7.1 复用方式

计划执行器由现有流程控制器改造（`internal/flowrun/controller.go`），不另写一套：

```text
制图计划 ──（planexec.Build）──► 可执行计划（复用 flow.FlowPlan / StepPlan 结构）──► flowrun.Controller
   steps            → StepPlan（Kind、Instructions、Completion、ExpectedOutputs、Refs、RequiredPackages）
   data(acquire)    → AcquisitionPlan 条目 + 隐式获取步骤（复用 v4 acquire_step）
   data(user/…)     → 有效输入（复用 v4 EffectiveInputs、逐行覆盖）
   guide resources  → Resources（复用资源解析与作用域）
```

新建 `internal/planexec/`：把制图计划转换为可执行计划，并处理修订。控制器增加 `StartFromPlan`、`Revise` 两个入口；按 FLOW.md 编译、执行条件、带类型的输入表单相关路径删除（`05`）。

### 7.2 按能力选角色

每个普通步骤的 `capabilities` 作为“所需工具包”，复用 v4 的解析与补齐（`internal/flow/roles.go`、`role_overlay.go`、`internal/agentruntime/flow_overlay.go`）：

1. `role_hint` 指定的方案角色：已启用且拥有所需工具包（或缺少的可临时补齐）时使用；
2. 拥有全部所需工具包的已启用方案角色，取多余工具包最少者；
3. 都没有时合成临时角色（职责取步骤标题与指南阶段名，模型取主角色模型）；
4. 系统专家：`路线知识抽取` 使用现有执行器（`internal/flowrun/executor_route_knowledge.go`）；`acquire` 步骤由获取引擎执行。

受限工具包（`pyqgis-scripting`、`creator-tools`、隐藏工具包）不补齐、不用于临时角色；需要时步骤失败并交回编排智能体。

### 7.3 每一步

| 环节 | 复用 |
|---|---|
| 资源作用域 | `resource.WithScope`（指南的资源与锁定） |
| 步骤消息 | `BuildStepMessage`，新增四段：【已知信息】（facts）、【可用数据】（有效路径与来源）、【本步图层】（图层处理表中 `layers` 对应的行）、【指南摘录】（`guide_sections` 对应原文与注意事项） |
| 回执 | 现有回执格式与修复（`readReceipt`） |
| 产出核验 | `VerifyOutputs`（文件、图层、版面、文本、数据集、审查结果） |
| 获取步骤 | v4 `acquire_step` 与获取引擎（后台开始、等待、逐行绑定、来源说明） |
| 事件与进度 | 现有 `flow.*` 事件，载荷增加 `plan_id`、`plan_version` |
| 运行记录 | `run.json` 增加 `carto_plan`（计划快照与历次修订）、`guide`（编号、版本、锁定摘要） |

### 7.4 最终检查

全部步骤完成后执行 `checks`：

| 检查写法 | 实现 |
|---|---|
| `版面元素包含 …` | 用 `layout_info`（`InvokeFlowTool` 已允许）读取版面元素比对 |
| `图层处理表中的图层都已在工程中` | 用 `get_layers_info` 比对 |
| `说明栏包含「…」` | 读取版面文本元素比对 |
| 其他 | 列为人工检查项写入交付摘要；计划含读图审查步骤时由审查步骤覆盖 |

检查失败视为最后一步失败，按 §8 处理。

## 8. 失败与重规划

1. 步骤失败后，执行器按现有规则自动重试一次（同一角色、附上失败原因）。
2. 仍失败时运行暂停（状态 `needs_replan`），发出 `flow.step_failed`（附诊断）。
3. 运行时向编排智能体发起一轮内部对话（界面显示“正在调整计划”），内容包括：计划、已完成步骤及产出、失败步骤的回执与核验错误。
4. 编排智能体二选一：
   - `plan_revise` 修订剩余部分（换数据来源、改步骤做法、增加修复步骤、删除可选步骤），执行器校验通过后从失败处继续；
   - `hitl_request` 请用户决定，失败卡选项：让智能体调整、我来提供数据、跳过（仅可选步骤）、停止。
5. 每次运行最多 3 次修订（README §9 第 8 项），之后停止并报告。

## 9. Plan 与 Build 模式

- **Plan 模式**：同一个编排智能体，只出计划不执行。工具限制为只读工具加 `plan_propose`（预览，不启动）、`data_find`、`hitl_request`；不联网获取数据。计划卡显示“切换到 Build 后执行”，切换后可一键执行同一份计划（重新校验）。
- **Build 模式**：出计划并执行。
- 删除独立的规划智能体配置（方案 `plan.agents.planner`）与 `internal/agentruntime/planexecute_builder.go` 中的独立构建路径（README §9 第 3 项；旧方案中的该段配置读取时忽略并在保存时移除）。

## 10. 恢复与历史

- 进程重启后，未完成的运行按 `run.json` 恢复（复用现有恢复与资源变化检查）；`needs_replan` 状态的运行在恢复后重新交给编排智能体。
- 旧流程产生的 `run.json`（没有 `carto_plan`）只读显示，不能继续执行（`05` §3）。

## 11. 编排智能体的提示

- 默认方案的编排提示改写为：理解任务 → 读指南 → 澄清 → `data_find` → `plan_propose` → 结束本轮；失败时修订；简单任务直接委派；取数一律委派数据获取智能体或写入计划。
- 用户已有方案的编排提示不改；以上规则同时由系统消息注入（替代现有“可用流程”注入，`internal/websocket/flow_runtime.go` `injectAvailableFlows`），对所有方案生效。
- 编排智能体看到的能力清单：每个方案角色的显示名、职责与实际工具包，以及两个系统专家。
