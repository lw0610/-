# 01 非阻塞编译规范

实现任务：V10（基础计划与稳定输入键）、V11（分级增强缓存）、V12（后台编译任务）、V13（接口与运行入口）。

## 1. 现有同步编译调用点与改造

| 调用点 | 现在 | 改为 | 任务 |
|---|---|---|---|
| `GET /api/flows/{id}`（`handlers_flow.go:159` → `decorateFlow(…, false)` → `Inspect`） | 读缓存计划；没有或过期时前端再发强制编译 | 返回执行计划（`Plan`），附计划状态；不调模型 | V13 |

## 2. 基础计划

### 2.1 接口

```go
// BasePlan 只做确定性工作，永不调用模型。
func (c *Compiler) BasePlan(ctx context.Context, id, scheme string) (*FlowPlan, error)

// CheckDraft 对未保存的 FLOW.md 草稿做同样的确定性检查，不写任何文件、不调模型。
func (c *Compiler) CheckDraft(ctx context.Context, id, scheme, flowMD string) (*FlowPlan, error)

// Plan 返回执行计划 = 基础计划 + 已缓存的增强结果，并填写计划状态；永不调用模型。
func (c *Compiler) Plan(ctx context.Context, id, scheme string) (*FlowPlan, error)
```

`EnsureRunnable` 改为 `Plan` + "有错误级诊断则返回 `ValidationError`"；`Inspect` 由 `Plan` 取代；`Compile` 不再被任何请求路径调用，仅供后台任务内部使用（改名为 `enrich`，不导出）。

### 2.2 组成（全部确定性）

1. `Parse(FLOW.md)`：分节、输入、资源、步骤、条件、规则（现有）。
2. 确定性输入：类型来自显式属性或说明中的关键词，键为输入名称（见 `04` §2）；替代现在的 `fallbackInputs`。
3. 角色绑定：`bindRole`（现有）。
4. 条件规则：`parse_condition.go` 能转换的条件直接给出规则；不能转换的保留原文，并提示"运行时由模型判断"（现有诊断 `FLOW_CONDITION_UNPARSED`）。
5. 静态体检：`completeDiagnostics` 中不依赖模型输出的部分（角色不存在、角色缺工具包、步骤缺完成标准、引用未解析、前向引用、产出重复等）。
6. 资源链接：`linkSource`（现有，v2 R40 已实现，链接记忆照旧）。

### 2.3 记忆

进程内按 `(FLOW.md 的 sha256, 结构环境修订号, 链接指纹)` 记忆基础计划。**结构环境修订号**只包含基础计划用到的东西：方案中各角色的编号、显示名、类型、执行器、启用状态、实际工具列表，以及能力目录中这些工具的名称与显示名；**不包含** `config.yaml` 修订号、启用流程列表、界面设置。

## 3. 增强结果与缓存

### 3.1 增强内容

| 级别 | 字段 | 应用规则 |
|---|---|---|
| 流程级 | `triggers`（触发词）、`input_types`（仅对未写类型属性的输入补全类型与选项）、`input_constraints` | 显式属性优先，模型不得改写；**不再生成输入键** |
| 步骤级 | `suggested_tools`、`missing_capabilities`、`expected_outputs`（仅当步骤没有声明产出时采用）、`condition`（仅当确定性解析没给出规则时采用）、`notes` | 与现在 `inferStep` 相同 |

模型提示与校验沿用 `compile_llm.go` 现有实现，只做两处修改：给模型的输入列表使用稳定键（输入名称）；资源摘要去掉 `entry_count`（避免数据变化影响增强）。

### 3.2 内容键

```text
flowKey = sha256(CompilerVersion, 模型名,
                 流程名称, 适用场景原文,
                 每个输入声明的 {名称, 属性原文, 说明})

stepKey = sha256(CompilerVersion, 模型名,
                 步骤声明 {标题, 负责角色原文, 做法, 完成标准, 声明的产出, 条件原文},
                 绑定到的角色 {编号, 实际工具列表（排序）},
                 本步候选能力 {名称, 显示名, 说明}（与发给模型的完全一致）,
                 输入 {名称, 类型},
                 资源摘要 {标签, 类型},
                 前序步骤的产出标签)
```

- **不进键**：`config.yaml` 修订号、方案名、启用流程列表、其他角色、完整能力目录、数据文件、绑定、输入记忆。
- 只改一个步骤 → 只有该步骤的键变化；改某个角色的工具 → 只有该角色负责的步骤变化；换模型 → 全部变化（合理）。
- `CompilerVersion` 升为 `"3"`，旧缓存自然失效。

### 3.3 存储

位置：`$AUTOCARTO_HOME/data/flow_cache/<流程编号>/enrich/`，不再按方案分目录（键已包含角色与工具）。

```json
{
  "api_version": "flow-enrichment/v1",
  "kind": "step",
  "key": "sha256:…",
  "flow_id": "marching-route",
  "step_title": "加载底图",
  "compiler_version": "3",
  "model": "deepseek-v4-pro",
  "created_at": "2026-10-22T12:00:00Z",
  "duration_ms": 12345,
  "attempts": 1,
  "result": { "suggested_tools": [], "missing_capabilities": [], "expected_outputs": [], "condition": null, "notes": "" }
}
```

- 文件名 `flow-<key 前 16 位>.json` / `step-<key 前 16 位>.json`；写入用临时文件 + 原子重命名（现有 `savePlan` 的做法）。
- 失败也记录：`{"kind": "step", "key": …, "failed": true, "reason": "timeout|invalid_json|provider_error|cancelled", "at": …}`。非强制任务跳过距今不足 `retry_after_seconds`（默认 600 秒）的失败记录，避免反复冲击模型；强制任务重试全部。
- 清理：每次任务结束后，保留当前各方案 FLOW.md 引用到的键，其余按修改时间只留最近 200 个文件。
- 旧的 `flow_cache/<流程>/<方案>/*.plan.json` 不再读取，V11 首次运行时删除。

### 3.4 合并与计划状态

`FlowPlan` 新增字段：

```go
PlanStatus string           `json:"plan_status"` // ready | enriching | partial | basic
Enrichment EnrichmentStatus `json:"enrichment"`
// EnrichmentStatus: {Done, Total int; JobID, JobState string; Failed []StepFailure; UpdatedAt time.Time}
```

`StepPlan` 新增 `Enrichment string`（`ready` | `pending` | `failed` | `none`）。

- 步骤有当前键的增强结果 → 应用；否则使用基础计划的值。
- `ready`：流程级与全部步骤都有当前键的结果；`enriching`：有进行中的任务；`partial`：有缺失且没有进行中的任务（失败或尚未触发）；`basic`：没有可用的编译模型。
- 诊断：失败的步骤报 `FLOW_COMPILE_LLM_FAILED`（警告，沿用现码）；任务进行中报 `FLOW_PLAN_ENRICHING`（提示）。**删除**"执行计划已过期，请重新解析"（`FLOW_PLAN_STALE`）这类阻塞性提示——执行计划永远是当前的。
- 兼容：流程详情中的 `stale` 字段从 V13 起固定为 `false`（旧前端据此不再发起同步编译），V21 完成后删除；登记兼容层。

## 4. 后台编译任务

### 4.1 管理器

新文件 `carto_agent/internal/flow/enrich_jobs.go`：

```go
type EnrichmentManager struct { /* 单例；由 cmd/agent/main_deep.go 创建并 Start(lifecycleCtx) */ }

func (m *EnrichmentManager) Enqueue(flowID, scheme string, opts EnqueueOptions) CompileJobStatus
// EnqueueOptions{Force bool; Reason string /* saved|created|imported|copied|selected|opened|manual */}
func (m *EnrichmentManager) Status(flowID, scheme string) (CompileJobStatus, bool)
func (m *EnrichmentManager) Cancel(flowID, scheme string) bool

type CompileJobStatus struct {
    JobID, FlowID, Scheme, Reason string
    State       string // queued | running | succeeded | failed | cancelled
    Done, Total int
    Failed      []StepFailure // {StepID, Title, Reason}
    StartedAt, FinishedAt *time.Time
}
```

规则：
- **去重**：同一 (流程, 方案) 同时只有一个任务。任务进行中再次入队：若 FLOW.md 或缺失键集合已变化，取消当前任务并重新开始（已完成的步骤结果已落盘，不会重做）；否则直接返回当前任务状态。
- **上下文**：来自进程生命周期 `lifecycleCtx`（`cmd/agent/main_deep.go:60`），**不使用请求上下文**；每个任务另有总超时，每次模型调用另有单次超时。
- **并发**：全进程共享一个模型调用信号量，默认 3。流程级增强先做；步骤之间互不依赖，按顺序提交、并发执行。
- **逐步落盘**：每个步骤成功或失败都立即写入 §3.3 的缓存，并推送一次事件。
- **强制**：`Force` 时忽略该流程已有的增强结果与失败记录，全部重做并覆盖。
- **没有模型**：环境中没有可用编译模型时不创建任务，计划状态为 `basic`。
- **重启**：进程重启后不自动恢复任务；下一次触发时只补做缺失的键。

### 4.2 触发时机

| 时机 | 行为 |
|---|---|
| 保存、新建、导入、复制成功后 | `Enqueue(Reason: saved/created/imported/copied)` |
| 流程中心打开某个流程详情、对话页选中流程，且计划状态为 `partial` | 前端调用 `POST /compile`（`force: false`）入队，不等待 |
| 点击"重新编译" | `Enqueue(Force: true, Reason: manual)` |
| 方案、工具目录、模型变化 | 不立即编译；相关步骤的键变化后自然成为"缺失"，等下一次触发 |
| 进程启动 | 默认不预编译（`flow_compile.warm_enabled_flows: false`），避免启动时集中调用模型 |

### 4.3 事件与轮询

- 事件：任务状态每次变化，通过注入的广播函数推送 WebSocket 消息 `flow_compile`（新消息类型，写入 `carto_agent/internal/websocket/protocol.go`，广播方式与现有 `broadcastSkillCatalogChanged` 相同），数据为 `CompileJobStatus` 的 JSON。
- 前端在 `WebSocketProvider.tsx` 中转成浏览器事件 `autocarto:flow_compile`（与 `autocarto:skill_catalog_changed` 同样的做法）。
- 轮询兜底：`GET /api/flows/{id}/compile-status?scheme=` 返回当前或最近一次任务状态。

### 4.4 日志

后端日志按下列格式记录（不记录提示词正文、模型输出正文和任何凭据）：

```text
[INFO] 流程编译任务开始 flow=marching-route scheme=default job=… reason=saved missing=9/12
[INFO] 流程编译调用 flow=marching-route step=s3 model=deepseek-v4-pro attempt=1 elapsed_ms=8123 ok=true
[WARN] 流程编译调用失败 flow=marching-route step=s7 reason=timeout elapsed_ms=90000
[INFO] 流程编译任务结束 flow=marching-route job=… state=succeeded done=12 failed=0 elapsed_ms=41230
```

### 4.5 配置

`config.yaml` 新增（`carto_agent/internal/config/config.go`）：

```yaml
flow_compile:
  provider: ""               # 为空时沿用现有选择（主角色模型，否则当前激活模型）；可指定更快的模型（已确认事项 4）
  concurrency: 3             # 同时进行的模型调用数
  call_timeout_seconds: 90   # 单次模型调用超时
  job_timeout_seconds: 900   # 单个任务总超时
  retry_after_seconds: 600   # 非强制任务对失败步骤的重试间隔
  warm_enabled_flows: false  # 启动后是否预编译已启用流程
```

修改这些配置不会使增强结果失效（只有模型名进入内容键）。

## 5. 接口

| 接口 | 行为 |
|---|---|
| `GET /api/flows?scheme=` | 流程列表，附每个流程的 `plan_status` 与诊断统计；不调模型 |
| `GET /api/flows/{id}?scheme=` | 详情 + 执行计划 + 计划状态；不调模型、不入队 |
| `PUT /api/flows/{id}?scheme=` | 保存；返回执行计划；入队（`saved`） |
| `POST /api/flows`、`POST /api/flows/import`、`POST /api/flows/{id}/copy` | 写入；返回执行计划；入队 |
| `POST /api/flows/{id}/check {scheme, flow_md?}` | 体检：有 `flow_md` 时检查草稿（`CheckDraft`），否则检查已保存版本（`Plan`）；不调模型 |
| `POST /api/flows/{id}/compile {scheme, force}` | 入队，立即返回 `202` 与 `{job, plan, diagnostics}`：`job` 为 `CompileJobStatus`，`plan` 为当前执行计划（不等待任务）。保留 `plan`、`diagnostics` 是为了让 V20 之前的旧前端继续可用；`force: false` 时只补缺失 |
| `GET /api/flows/{id}/compile-status?scheme=` | 任务状态 |
| `DELETE /api/flows/{id}/compile?scheme=` | 取消进行中的任务 |

## 6. 运行入口与运行策略

- `flowrun.Controller.Start`、恢复、`flow_preview`、`flow_start`、`AvailablePlans` 一律使用 `Plan`（执行计划），不调模型。
- 计划状态不是 `ready` 时（已确认事项 1：不等待）：照常运行；`run.json` 的计划快照记录 `plan_status` 与各步骤 `enrichment`；步骤消息中未完善的步骤不写"建议使用的能力"。对话页在发送前显示一句"有 N 个步骤尚未完善，将按基础计划运行"。
- `AvailablePlans` 给编排模型的摘要中，没有触发词时用流程名称与适用场景代替（现在已有适用场景字段）。

## 7. 验收计数（V50 测试）

用两种假模型：计数模型（立即返回合法 JSON）、慢模型（每次调用睡眠，可被取消）。

| 场景 | 期望 |
|---|---|
| `GET` 详情、`GET` 列表、保存、新建、导入、复制、体检（含草稿）、`AvailablePlans`、`Start` | 请求内模型调用 0 次；保存类请求返回后后台任务被创建 |
| 慢模型 + 发起编译后立即断开请求 | 任务继续；完成后缓存中有全部步骤结果 |
| 任务进行中进程内取消（模拟关闭） | 已完成步骤的结果保留；重新触发后只补做剩余步骤 |
| 只改第 3 步的"做法" | 新任务只调用 1 次步骤级模型（流程级不变） |
| 修改 `config.yaml` 中与编译无关的项、启停另一个流程 | 计划状态保持 `ready`，模型调用 0 次 |
| 第 5 步模型超时 | 其他步骤为 `ready`；第 5 步为 `failed`，诊断 `FLOW_COMPILE_LLM_FAILED`；流程仍可运行 |
| 同一流程并发入队 5 次 | 只有 1 个任务 |
