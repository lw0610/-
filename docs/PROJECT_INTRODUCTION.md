# AutoCarto / Eino 项目介绍

## 1. 项目概述

AutoCarto / Eino 是一个面向 GIS 自动化制图、空间分析和智能体协作的综合系统。项目以 QGIS 为专业 GIS 执行环境，以 Go 后端作为运行时控制面，以前端桌面应用作为可视化管理入口，通过工具契约、技能包和多智能体配置，把传统 GIS 操作流程转化为可编排、可调用、可追踪的自动化能力。

项目的核心目标不是简单封装若干 GIS 工具，而是建立一套“自然语言任务理解 - 专业智能体分工 - 工具调用 - QGIS 执行 - 结果回传 - 运行态治理”的闭环体系。用户可以围绕数据加载、空间处理、专题制图、版面布局、地图导出等任务进行交互，系统根据 agent 配置和 skill package 暴露相应能力，并通过运行时 descriptor 保证工具执行契约的一致性。

从定位上看，本项目兼具三个属性：

1. GIS 专业工具平台：沉淀 QGIS、PyQGIS、处理算法和制图布局能力。
2. 智能体运行平台：通过 orchestrator、cartographer、data_engineer、spatial_analyst 等角色拆分复杂任务。
3. 工具治理平台：以统一契约管理工具定义、可见性、执行绑定、agent 挂载和运行态诊断。

## 2. 系统架构

项目主要由三层组成：

| 模块 | 路径 | 主要职责 |
|---|---|---|
| QGIS 插件层 | `autocarto/` | 运行在 QGIS 环境中，负责读取运行时 descriptor、注册工具、执行 PyQGIS/QGIS 工具、通过 WebSocket 回传结果 |
| Go 控制面 | `carto_agent/` | 负责后端 API、WebSocket、agent 配置、skill/tool catalog、runtime descriptor、工具调用路由和运行态治理 |
| 桌面前端 | `autocarto-web/` | 基于 Next.js + Tauri，提供配置、诊断、工具中心、运行态可视化和用户交互入口 |

整体链路如下：

```text
用户任务
  -> 前端或会话入口
  -> Go 后端智能体编排
  -> skill package 决定可用工具范围
  -> tool catalog / execution manifest 下发
  -> QGIS 插件注册并执行工具
  -> tool_result 回传
  -> 结果、日志、输出文件进入会话上下文
```

这个架构将“工具是否能看到”“工具如何执行”“工具是否可公开”分成不同治理层，避免工具文件、智能体提示词和运行时执行入口混在一起。

## 3. 关键实现机制

### 3.1 运行时 Descriptor 机制

插件侧不再直接扫描本地工具目录作为唯一依据，而是通过后端下发的 `/api/runtime/descriptor` 获取权威运行时契约。descriptor 中包含：

- `execution_manifest`：插件真正用于注册执行的工具绑定清单。
- `tool_catalog`：对外公开的工具目录视图。
- WebSocket 地址、运行态状态、实例信息等连接元数据。

这种方式的优势是：后端成为 authority，插件只消费已经治理过的执行契约，从而减少本地缓存、目录漂移、工具暴露不一致等问题。

### 3.2 工具契约与执行绑定

系统支持 `tool/v1`、`tool-package/v1`、`tool_contract/v1` 等工具定义形态。一个工具通常包含：

- `metadata`：工具名称、domain、runtime。
- `spec`：描述和参数。
- `execution`：handler、handler_file、handler_function、backend_tool 或 CLI 执行方式。
- `policy`：可见性、授权范围、发布策略。

对于 QGIS/PyQGIS 工具，常见链路是：

```text
共享实现 _shared/*.py
  -> 工具包 handlers/*.py 导出 handler
  -> tools/system/<domain>/<tool>.yaml 定义工具
  -> skill package 的 tools 列表暴露工具
  -> agent.yaml 挂载 skill package
  -> runtime descriptor 下发执行绑定
```

这条链路使工具注册、执行和暴露各自清晰，也便于排查“工具实现存在但 agent 看不到”或“agent 看得到但插件没注册”的问题。

### 3.3 Skill Package 与多智能体分工

系统将能力组织为 skill package。部分 skill 是工具集合，例如 `cartography-styling`、`print-layout`、`data-loading`；部分 skill 是工作流或知识约束，例如行军路线图制图流程、专题图制图流程等。

默认智能体配置中包含多个专业角色：

- `orchestrator`：理解任务、路由专业 agent、控制流程。
- `data_engineer`：数据加载、字段整理、CRS 检查、数据格式转换。
- `spatial_analyst`：空间分析、几何处理、网络分析、栅格分析。
- `cartographer`：地图符号化、标注、布局、导出。
- `scripting_specialist`：在标准工具不足时处理 PyQGIS 脚本和复杂自动化。

这种设计不是把所有工具直接暴露给一个单体 agent，而是用“角色 + skill package + 工具目录”约束能力边界，让任务执行更可控。

### 3.4 QGIS 工具执行闭环

插件在 QGIS 内部执行工具，能够访问项目、图层、布局、画布、Processing 算法和 PyQGIS API。后端通过 WebSocket 发起 `tool_invoke`，插件执行后回传 `tool_result`，形成端到端闭环。

对于制图场景，系统已经沉淀了符号化、标注、贝塞尔箭头、军标箭头、点符号映射、布局元素、比例尺、指北针、图例、导出 PDF 等能力。这使它更接近“自动制图生产线”，而不是单个脚本工具集合。

## 4. 技术亮点

### 4.1 工具治理与执行解耦

项目最大的技术亮点之一是把工具治理和工具执行分离。Go 后端负责定义权威目录、可见性和 agent 暴露策略；QGIS 插件只负责执行 descriptor 下发的工具绑定。这种模式提升了系统一致性，也让工具扩展、权限控制和运行态诊断更容易落地。

### 4.2 多智能体与 GIS 专业流程结合

项目不是泛化聊天机器人，而是把智能体体系嵌入 GIS 业务流程。不同 agent 对应不同专业边界，例如数据工程、空间分析、制图布局和脚本兜底。复杂制图任务可以被拆解为多个专业阶段，既能利用大模型的任务规划能力，又能保留 GIS 工具链的确定性。

### 4.3 Descriptor 驱动的运行态发现

运行态 descriptor 让插件、后端和前端围绕同一份契约协作。系统可以在 ready、block、degraded 等状态之间切换，并携带工具 catalog、实例状态和运行时修订信息。这种设计适合桌面 GIS 场景，因为 QGIS 插件、后端服务和前端桌面应用往往不是同一个生命周期。

### 4.4 面向 PyQGIS 的工程化封装

传统 PyQGIS 自动化脚本常常难以复用、难以治理、难以暴露给非开发用户。本项目通过 handler wrapper、共享实现、参数映射、输出目录管理、主线程调用保护和 JSON 结果规范化，把 PyQGIS 能力沉淀成可被 agent 稳定调用的工具单元。

### 4.5 制图工作流的高阶抽象

项目中的制图能力不仅包含“设置样式”这种基础操作，也包含版面布局、符号映射、箭头绘制、图文标注、导出等组合能力。对于交通路线图、专题图、行军路线图等任务，系统可以把地图表达、布局约束和输出质量要求写入 workflow skill，从而形成可复用的制图方法模板。

## 5. 研究方法亮点

### 5.1 从人工 GIS 操作到可编排流程

本项目的研究方法可以概括为：先分析人工 GIS 制图和空间分析中的操作链，再将操作链拆分为可参数化工具，最后通过 agent 编排实现自动执行。这种方法兼顾了专业流程的真实性和自动化系统的可扩展性。

### 5.2 工具契约化方法

每个工具都通过 schema、参数、执行绑定和可见性策略描述自身能力。这相当于为 GIS 操作建立“可机器理解的能力说明书”。相比直接写脚本，契约化方法更适合大规模工具集管理、智能体调用和运行时审计。

### 5.3 分层验证方法

项目可以按层验证：

1. 工具定义层：检查 YAML/contract 是否完整。
2. 执行绑定层：检查 `execution_manifest` 是否包含目标工具。
3. 暴露层：检查 `tool_catalog` 和 skill package 是否允许当前 agent 使用。
4. 执行层：通过真实 `tool_invoke -> tool_result` 验证闭环。

这种验证方法比只看代码是否存在更可靠，尤其适合多进程、多语言、多运行时的桌面 GIS 智能系统。

### 5.4 面向场景的工作流沉淀

项目不是只做底层能力堆叠，而是把制图场景中的规则、约束和质量标准写入 workflow skill。例如专题图、行军路线图、打印布局等任务，都可以沉淀为可重复调用的流程知识。这使研究方法从“工具开发”进一步走向“知识工程 + 工具执行”的结合。

## 6. 研究方向亮点

### 6.1 GIS 与智能体系统融合

本项目处在 GIS 自动化和 AI Agent 交叉方向。它探索的不只是“让大模型回答 GIS 问题”，而是让大模型通过受控工具链真正操作 GIS 环境，完成数据处理、地图表达和成果输出。

### 6.2 可治理的专业智能体

很多智能体系统强调开放工具调用，但在专业软件场景中，工具边界、参数安全、执行状态和结果追踪更重要。本项目通过 authority manifest、tool catalog、agent config 和 skill package 建立治理体系，适合研究“可控、可审计、可扩展的专业智能体”。

### 6.3 智能制图与自动版面设计

制图不是单纯的数据渲染，还涉及符号体系、视觉层级、标注避让、版式构图和输出规范。本项目围绕 cartography、print-layout 等能力构建自动化流程，为智能制图、自动地图设计和行业制图模板化提供了研究基础。

### 6.4 人机协同 GIS 工作流

项目保留了 HITL、运行态诊断、配置可视化和工具目录治理等机制，适合进一步研究人机协同模式：哪些步骤由 agent 自动完成，哪些步骤需要人工确认，哪些步骤可以通过规则兜底。这对高风险 GIS 任务和行业制图交付很关键。

## 7. 应用场景与市场价值

### 7.1 专题地图生产

系统适用于人口、交通、土地利用、生态环境、可达性、灾害风险等专题图生产。通过固定 workflow 和工具链，可以降低重复制图成本，提高输出一致性。

### 7.2 交通与路线制图

项目中的路线符号化、箭头绘制、布局排版和标注能力，适合交通路线图、行军路线图、路径规划成果图等场景。对于需要快速生成高质量地图成果的业务，有较强落地价值。

### 7.3 空间分析成果自动出图

空间分析往往停留在结果图层生成阶段，而最终交付仍需要地图表达和布局。本项目可以把分析结果继续推进到符号化、图例、比例尺、指北针、说明文字和 PDF 导出，补齐“分析到成果”的最后一段。

### 7.4 GIS 教学与科研辅助

对于教学和科研场景，系统可以帮助用户理解标准 GIS 工作流，将数据处理、制图表达和报告输出过程结构化。它也适合用于演示智能体如何与专业桌面软件协作。

### 7.5 行业软件插件化扩展

项目采用插件、工具契约和 skill package 体系，具备持续扩展行业工具包的能力。未来可以面向自然资源、应急管理、交通规划、水文分析、可视域分析、国土空间规划等方向扩展专用 agent 和工具集。

## 8. 项目优势总结

本项目的综合亮点可以概括为：

1. 技术上：实现了 QGIS 插件、Go 控制面和前端桌面应用的协同架构，并通过 descriptor 和工具契约保证运行时一致性。
2. 方法上：将 GIS 专业操作拆解为可治理工具，再通过 skill 和 agent 组合成可复用工作流。
3. 方向上：切入 GIS 自动化、智能制图、专业智能体和人机协同工作流的交叉研究方向。
4. 应用上：面向专题制图、空间分析成果出图、交通路线图、行业报告和批量制图等场景，具备明确落地空间。

一句话概括：AutoCarto / Eino 的价值在于把专业 GIS 软件从“人工操作工具”推进为“可被智能体理解、编排和执行的空间智能生产平台”。

## 9. 后续发展方向

后续可以从以下方向继续完善：

1. 增强工具注册校验，自动提示工具缺失于 `execution_manifest`、skill `tools` 列表或 agent 配置的问题。
2. 扩展制图质量评估，例如布局元素重叠检测、标注可读性检查、导出成果审查。
3. 建立更多行业 workflow skill，例如应急制图、规划审查图、流域分析成果图、可达性专题图。
4. 引入任务过程记录和可复现实验日志，方便科研评估和工程审计。
5. 加强人机协同节点，在高风险步骤前提供确认、预览和回滚机制。
