# 03 运行机制：流程执行器

本文定义流程怎么运行。实现任务：T30（执行器核心）、T31（接入）、T32（前端）、T33（专用执行器）。

## 1. 总体设计

**流程执行器（FlowRunner）是一个控制器，不是一个大模型智能体。** 它按执行计划逐步推进：每一步都作为一次独立的智能体运行（root agent 就是负责该步的角色智能体），运行结束后控制器读取回执、校验产出，再决定下一步。

选择"每步一次独立运行"而不是"在一个智能体里嵌套子智能体"，原因是：
- 现有的会话运行机制已经处理好了流式事件、人工确认中断与恢复、取消、checkpoint 持久化（`internal/websocket/phase_runner.go` 的 `runAgentPhase`、`task_runner.go` 的 `consumeEvents`、`resumeTask`）。每一步直接复用它们，步骤内部的 `hitl_request` 和知识审查中断不需要任何新机制。
- Plan→Build 两阶段运行（`processTask` 先跑 plan 再跑 build）已经是"一次任务多次运行"的先例，流程是它的推广。
- Eino ADK 里把外部子智能体的中断组合起来需要用到包内未导出的实现（`adk/workflow.go` 的顺序工作流依赖 `internalInterrupted`、`updateRunPathOnly`），在包外复刻风险高。

```text
               ┌──────────── 控制器 internal/flowrun.Controller ────────────┐
task 消息 ──►  │ 准备输入 → 逐步：判断条件 → 组装步骤消息 → 启动一次运行      │
(指定流程)     │   ↑                         │                              │
               │   │      runAgentPhase(角色智能体, [步骤消息], runID)        │
flow_start ──► │   │                         │（中断→等待用户→resumeTask）   │
(编排工具)     │   └── 读回执 → 校验产出 → 失败策略 → 写 run.json → 推送事件 │
               └─────────────────────────────────────────────────────────────┘
```

## 2. 启动方式

### 2.1 前端指定流程（推荐，最确定）

前端发送现有的 `task` 消息，在 `data` 里增加：

```json
{
  "flow": {
    "id": "marching-route",
    "inputs": {
      "source_text": {"$ref": "current_user_message"},
      "paper": "A1 横向",
      "quality_review": true
    }
  }
}
```

服务端收到后不经过编排智能体，直接启动控制器。`{"$ref": "current_user_message"}` 表示取本条消息原文。

### 2.2 对话中自动匹配

编排智能体获得一个内部工具 `flow_start`。它属于隐藏包"流程控制"（`flow-control`），该包只自动挂给 Build 模式的主智能体，其他角色拿不到，避免子智能体自行启动流程：

```json
{"flow_id": "marching-route", "inputs": {"source_text": {"$ref": "current_user_message"}, "paper": "A1 横向"}}
```

`flow_start` 的行为：
1. 检查流程在当前方案中已启用、执行计划没有错误级诊断（必要时先自动重新编译）。
2. 检查必填输入和输入约束。不满足时返回错误，列出缺少的输入名称和说明，编排智能体据此询问用户。
3. 满足时在会话运行状态中登记"待启动流程"，返回 `{"accepted": true, "flow_run_id": "…"}`。
4. 编排智能体本轮结束后（`consumeEvents` 返回且没有中断），服务端发现待启动流程，启动控制器。

编排智能体的提示词要求它启动流程后直接结束本轮，只回复一句"已启动流程「…」"。

### 2.3 Plan 模式

Plan 模式下命中流程时不执行，只做预览：规划智能体调用只读工具 `flow_preview(flow_id)`（放在 Plan 自动挂载的隐藏包"能力查询"中；"流程控制"包里也有一份供编排智能体使用），返回步骤列表、诊断和输入检查结果。前端把它渲染成与流程中心相同的步骤预览卡片。用户切到 Build 后再运行。

## 3. 编排智能体通用提示词（目标文本，T51 写入默认方案）

```text
你负责理解用户需求、选择执行方式，并在最后汇总结果。

1. 先判断任务是否适合下方"可用流程"中的某一个。适合时：
   - 按该流程"需要准备"整理输入；原文类输入一律传 {"$ref":"current_user_message"}，不要复述或摘要原文。
   - 必填输入缺失时，先询问用户，不要编造。
   - 输入齐全后调用 flow_start，然后只回复一句"已启动流程「流程名称」"，结束本轮。流程运行期间不要自行委派其他智能体。
2. 没有合适的流程时，按各专业智能体的职责分工委派。每次委派只说明目标和必要上下文，不替专业智能体决定具体工具和参数。
3. 汇总时以工具返回、流程运行记录和各智能体回报的真实结果为准，不编造路径、数量或结论；失败和未完成的部分要如实说明。
4. 高风险、不可逆或存在关键歧义的操作，先用 hitl_request 请用户确认。
```

"可用流程"段由 `TemplateEngine.BuildOrchestratorPrompt`（`internal/deepagent/subagents/template_engine.go`）按当前方案已启用且没有错误级诊断的流程自动生成：

```text
## 可用流程
- 行军路线图（flow_id: marching-route）
  适用场景：……（FLOW.md 适用场景原文，超过 300 字截断）
  需要准备：史料原文（与路线数据集二选一）；路线数据集（与史料原文二选一）；纸张（默认 A1 横向）；质量审查（默认否）
```

## 4. 控制器主循环

```text
Start(session, flowID, rawInputs, origin):
    plan := EnsureCompiled(flowID, scheme)              // 缓存键变化则重编译
    if plan 有错误级诊断: 推送 flow_blocked，结束
    inputs := ResolveInputs(plan, rawInputs, 当前消息)    // $ref 展开、类型转换、默认值
    if 缺必填或违反约束: 推送 flow_blocked（列出缺项），结束
    run := NewRun(plan, inputs, origin); 写 run.json; 推送 flow_started
    Advance(run)

Advance(run):
    while run.cursor < len(plan.steps):
        step := plan.steps[run.cursor]
        if !EvalCondition(step, run): 标记 skipped，cursor++，写 run.json，推送事件，continue
        agent, input := BuildStepRun(step, run)          // 见 §5–§7、§11–§12
        runID := fmt.Sprintf("flow-%s-s%02d-a%d", run.id, step.index, attempt)
        result := runAgentPhase(ctx, …, agent, input, options{runID, originalSource: run.原文, 不发最终回复, 过程消息带 flow_run_id 标记})
        if result.Interrupted:
            登记 runID → run，标记"等待恢复"；标记 waiting_user，写 run.json，推送事件
            return                                       // 用户处理后，由 §14 的回调调用 OnStepRunFinished
        next := OnStepRunFinished(run, runID, result)    // 同步路径：控制器自己处理结果
        if next != continue: return                      // 已结束、已失败或在等待用户选择
    Finish(run)

OnStepRunFinished(run, runID, result) -> next:   // 同步路径直接调用；恢复路径由回调调用
    receipt := ReadReceipt(step, result)          // §8；专用执行器走适配器 §12
    check := VerifyOutputs(step, receipt)         // §9
    if receipt.status == completed && check.ok:
        记录产出，标记 completed，cursor++，写 run.json，推送 flow_step_completed
        return continue
    else:
        return ApplyFailurePolicy(run, step, receipt, check)   // §10：continue（重试或跳过）/ wait_user / stop

恢复回调(runID, result):
    run := 查找登记为"等待恢复"的 runID；清除标记
    if OnStepRunFinished(run, runID, result) == continue: Advance(run)
```

约束：
- 一个会话同一时间只能有一个进行中的流程。流程运行期间，用户的新消息沿用现有"任务进行中"的保护逻辑。
- 控制器不调用编排智能体。只有两处可能调用模型：条件判断（无法转成规则时，§13）和回执修复（§8.2）。两者都使用编排智能体的模型，温度 0，输出受约束 JSON。
- `runAgentPhase` 目前用输入里最后一条用户消息作为"原文"（`knowledge.WithOriginalSource`）。流程步骤的输入是步骤消息，所以必须新增参数，让控制器显式传入流程的原文，否则知识抽取会把步骤消息当成史料。

## 5. 角色智能体工厂

在 `internal/deepagent` 中把 `createSubAgents` 里"构造单个角色智能体"的逻辑提取为：

```go
// BuildRoleAgent 按当前方案构造一个角色智能体：工具过滤、工具包使用说明中间件、模型选择与 createSubAgents 完全一致。
func BuildRoleAgent(ctx context.Context, cfg *Config, roleName string) (adk.Agent, error)
```

- 通用角色：返回与现在子智能体相同的 ChatModelAgent（同样的工具、同样的 skill 中间件），只是作为本次运行的 root agent。
- 专用执行器角色：按执行器类型返回对应智能体（§12）。
- `createSubAgents` 改为调用 `BuildRoleAgent`，保证自由委派和流程执行使用同一套构造逻辑。

## 6. 步骤消息模板

控制器为每一步渲染下面这条用户消息，空段落整段省略。模板放在 `internal/flowrun/templates/step_message.tmpl`，代码只负责填充，便于以后调整措辞而不改代码。

```text
你正在执行流程「{{.FlowName}}」的第 {{.Index}}/{{.Total}} 步：{{.Title}}。
只完成本步骤，不要做其他步骤的工作。

【本步骤要做的事】
{{.Instructions}}

【整个流程必须遵守】
{{range .Rules}}- {{.}}
{{end}}
【可用资源】
{{range .Resources}}- {{.Label}}（{{.TypeLabel}}）：{{.Description}}
{{end}}
【用户输入】
{{range .Inputs}}- {{.Label}}：{{.ValueSummary}}
{{end}}
【前面步骤的产出】（系统记录，内容准确，直接使用）
{{.UpstreamOutputsJSON}}

【建议使用的能力】（不限于此，可以使用你拥有的其他工具）
{{range .SuggestedTools}}- {{.Label}}（{{.Name}}）
{{end}}
【完成标准】
{{range .ExpectedOutputs}}- 「{{.Label}}」（{{.TypeLabel}}{{if .Required}}，必需{{end}}）
{{end}}
{{if .LastFailure}}【上一次尝试未通过】
{{.LastFailure}}
{{if .UserGuidance}}用户补充说明：{{.UserGuidance}}{{end}}
{{end}}
【完成后输出回执】
你的最后一条回复只能是一个 JSON 对象，不要加任何说明文字或代码块标记：
{"status":"completed","summary":"一句话说明本步做了什么","outputs":{"产出名称":"值"},"issues":[]}
- outputs 的键必须使用【完成标准】中的产出名称，值使用工具返回的真实路径、图层名、版面名或 ID，不要编造。
- 无法完成时 status 写 "blocked"（缺数据、缺能力、需要用户决定）或 "failed"（工具执行失败），并在 issues 写明原因。
```

各段内容的来源：
- `Resources`：本步引用的资源和全流程资源。数据清单列出每个条目的名称和实际路径；样式集给出目录路径和对照表摘要；版式给出内置版式名或 .qpt 路径；符号给出目录和对照表路径。
- `Inputs`：`conversation_text` 类型只写"见本次对话原文（系统已保存，工具会直接读取）"，不把原文塞进消息。
- `UpstreamOutputsJSON`：所有已完成步骤的产出，键为"第N步 标题"，值为该步 outputs，原样 JSON。超过 20 KB 时，只保留本步 `refs.outputs` 引用到的产出和每步的 summary，并在 run.json 里记录截断。

## 7. 运行选项

每一步调用 `runAgentPhase` 时：
- `runID`：`flow-<flow_run_id>-s<两位序号>-a<尝试次数>`，作为 checkpoint ID。
- `emitFinalResponse=false`：步骤的回执不作为最终回复推给用户，前端通过流程事件展示。
- `persistAssistant`：步骤内部过程照常记录到会话历史（便于排查），但标记 `flow_run_id` 和步骤序号，前端可以折叠显示。
- 工具调用、子智能体事件照常推送，前端在流程卡片下分组显示。

## 8. 回执

### 8.1 格式

```json
{
  "status": "completed | blocked | failed",
  "summary": "一句话",
  "outputs": {"产出名称": "值或 JSON"},
  "issues": ["问题或风险"]
}
```

读取规则：取本次运行最后一条助手消息（`consumeEventsResult.LastContent`）。依次尝试：整段解析为 JSON；去掉 Markdown 代码块标记后解析；截取最后一个顶层 `{…}` 解析。

### 8.2 回执修复

解析失败、缺少 `status` 或 `outputs` 不是对象时，调用一次模型（无工具，温度 0），输入为"该步完成标准 + 最后一条助手消息 + 本次运行中成功工具调用的结果摘要"，要求只输出回执 JSON。工具调用摘要由 `StepRunner` 在消费运行事件时顺带收集（每个成功工具调用保留工具名和结果的前 2 KB）；收集不到时只用最后一条消息。修复结果仍不合法时，按校验失败处理（§10）。修复的输入和输出都写进 run.json。

## 9. 产出校验

控制器拿回执里的 outputs 对照步骤的 `expected_outputs` 逐个检查。必需产出缺失即校验失败。按类型做确定性检查，需要查询 QGIS 时通过现有工具调用通道直接调用只读工具（参考 `deepagent/workflow_agent.go` 的 `invokeWorkflowTool` 写法）：

| 类型 | 检查 |
|---|---|
| `layers` | 调 `get_layers_info`，回执中的每个图层名或 ID 都存在 |
| `dataset` | 目录存在；`format=route_dataset` 时六张表都存在（places/routes/route_paths/points/symbol_mapping/callouts.csv）；`format=statistical_dataset` 时 manifest 存在 |
| `file` | 文件存在、大小大于 0；有 `format` 时扩展名一致 |
| `layout` | 调 `layout_info(name=<版面名>)` 成功 |
| `text` | 非空 |
| `review_initial` / `review_final` | 结构校验，见 §9.1 |
| `confirmation`、`any` | 不检查 |

### 9.1 审查结果结构校验

原来写在编排提示词里、要求编排智能体检查的规则，改由程序检查：

`review_initial`：
- 有 `dimension_results`，且恰好包含 8 个键：`overlap`、`layout`、`alignment_spacing`、`visual_hierarchy`、`typography`、`color`、`map_readability`、`style_consistency`；每项有布尔 `has_issue`。
- 任一 `has_issue=true` 时 `suggestions` 非空；`suggestions` 为空时 8 项必须全部为 false。
- 每条 suggestion 有 `suggestion_id`、`category`（属于上述 8 个）、`target_item_ids`（数组）、`executable`（布尔）；`executable=false` 时 `adjustment` 为 null；`executable=true` 时 `adjustment.tool_name` 非空。
- 有 `review_manifest_path` 和 `reserved_final_image_path`，且文件或目录位置合法。

`review_final`：
- 有布尔 `final_passed` 和数组 `remaining_issues`。
- `suggestion_results[*].status` 属于 `correctly_applied | partially_applied | not_applied | skipped | regression`。

校验规则实现为 Go 函数，放在 `internal/flowrun/verify_review.go`，并带单元测试。`final_passed=false` 不算步骤失败：步骤状态为 completed，但流程最终状态记为"完成但有问题"。

## 10. 失败策略

| `on_failure` | 行为 |
|---|---|
| `retry_then_ask`（默认） | 第 1 次失败：把失败原因（回执 issues、缺失产出、校验错误）写进【上一次尝试未通过】，重试一次。第 2 次失败：询问用户 |
| `ask` | 第 1 次失败就询问用户 |
| `stop` | 流程失败结束 |
| `skip` | 标记"失败后跳过"，继续下一步 |

**询问用户**：控制器启动一次"确认运行"，root agent 是一个很小的自定义智能体 `confirmAgent`（`internal/flowrun/confirm_agent.go`）。它在 `Run` 时用 `adk.StatefulInterrupt` 发出与现有 `hitl_request` 相同结构的中断卡片（复用 `internal/hitl` 的 `InterruptPayload` 格式，前端无需新组件），选项为"重试本步 / 跳过本步 / 终止流程"，并带补充说明输入框；`Resume` 时读取用户选择，输出 `{"choice": "retry|skip|stop", "guidance": "…"}` 作为最后一条消息。控制器在 `OnStepRunFinished` 里识别这是确认运行，按选择处理：重试时把补充说明放进【上一次尝试未通过】；重试不计入自动重试次数，但同一步最多重试 5 次。

## 11. 人工确认步骤

"负责：用户"的步骤（`kind=confirm`）同样用 `confirmAgent`：问题取自该步做法，选项默认"确认 / 不确认"，做法里用列表写了选项时使用这些选项。用户的选择作为该步产出（`confirmation` 类型）。选择"不确认"时按该步 `on_failure` 处理。

## 12. 专用执行器

专用执行器是角色类型 `kind: executor` 的角色，用固定程序完成一类任务。为避免包之间循环依赖，分三处定义：

```go
// internal/flow/executors.go —— 静态元数据，编译器体检用
type ExecutorSpec struct {
    Type               string   // 例如 "route_knowledge"
    DisplayName        string   // 例如 "路线知识抽取"
    RequiredInputTypes []string // 例如 ["conversation_text"]
}

// internal/deepagent —— BuildRoleAgent 按 executor 类型构造智能体（知识执行器本来就在这个包里）

// internal/flowrun/executor.go —— 输入与回执的适配
type ExecutorAdapter interface {
    Type() string
    BuildInput(step flow.StepPlan, run *RunState) ([]*schema.Message, error) // 生成这次运行的输入消息
    ToReceipt(step flow.StepPlan, lastContent string) (Receipt, error)      // 把执行器输出转成回执
}
```

依赖方向：`flowrun` → `flow`；`websocket` → `flowrun`、`deepagent`；`flow` 和 `flowrun` 都不导入 `deepagent`。

`route_knowledge`（路线知识抽取，T33 实现）：
- 构造：`BuildRoleAgent` 返回现有 `knowledgeSubAgent`（`internal/deepagent/knowledge_agent.go`）。
- `BuildInput`：生成 JSON 用户消息 `{"source_ref":"current_user_message", "rules": <该步做法>, "force_refresh": <布尔>, "symbol_assets_dir": <符号资源目录>, "symbol_table": <符号对照表路径>, "route_style_table": <路线样式资源路径>}`。
  - 原文：本步引用的 `conversation_text` 类型输入（体检要求必须存在）；原文本身由控制器通过 `originalSource` 传入上下文。
  - `force_refresh`：本步引用的输入中，名称为"重新抽取"的是/否输入；没有时为 false。执行器只按这个固定名称识别，FLOW.md 模板和示例中使用同一名称。
  - 资源：按本步引用资源的类型取值（`symbols` → `symbol_assets_dir` 与 `symbol_table`，`route_style` → `route_style_table`）；没有引用时不传，由编译器使用内置默认资源。
- 规则来源：该步"做法"非空时用它作为抽取业务规则；为空时退回角色的 `static_instructions`。规则参与现有抽取结果复用的兼容性哈希，行为与现在一致。
- `ToReceipt`：执行器最后输出 `{"success": true, "data": {…}}`，映射为 `status=completed`，`outputs` 中该步第一个 `dataset` 类型的产出取 `data.dataset_dir`，并原样附带 `artifact_id`、`task_id`、`task_graph_file`、`counts`、`validation`、`warnings`。
- 中断：知识审查中断照常发生，用户在审查卡片中确认后，现有的 `knowledge_review_resume.go` 恢复运行；运行结束时经 §14 的恢复回调交给控制器。
- 专用执行器角色带 `flow_only: true`，不出现在编排智能体可自由委派的列表里。

## 13. 条件判断

- 有 `rule` 时按 `02` 文档 §8 用代码求值。
- 只有文字时，调用一次模型：输入"条件原文 + 输入摘要 + 已完成步骤的状态和 summary"，输出 `{"run": true|false, "reason": "…"}`。结果和理由写入 run.json，并在流程卡片上显示。

## 14. 恢复回调点

- 没有中断的运行：控制器同步等待 `runAgentPhase` 返回并自己处理结果，不经过回调。
- 被中断的运行：控制器在返回前把 runID 登记为"等待恢复"。用户处理后，运行由 `resumeTask` 或知识审查确认（`knowledge_review_resume.go`）恢复，两者最终都经过 `consumeEvents`。在 `consumeEvents` 返回、结果不是 Interrupted 时，按 runID 查找"等待恢复"登记，有则清除登记并调用控制器的恢复回调（§4）。没有登记的 runID 一律忽略，因此同一次运行不会被处理两次。
- 恢复后再次中断：保持登记，等待下一次恢复。

## 15. 自动选择角色

`kind=auto` 的步骤：在已启用的通用角色中，选建议能力覆盖最多的角色；并列时按方案中的角色顺序选第一个；建议能力为空时选编排智能体以外的第一个角色，并在体检中提示 `FLOW_STEP_NO_ROLE`。

## 17. 事件协议

新增消息类型 `flow_event`（`internal/websocket/protocol.go`），并在 `normalizeRunEventType` 中映射为统一运行事件，事件名如下：

| `event` | 时机 | `payload` 主要字段 |
|---|---|---|
| `flow.started` | 流程开始 | `flow_run_id, flow_id, name, steps: [{id, index, title, role_label, kind}]` |
| `flow.blocked` | 启动前检查不通过 | `flow_id, reasons: [{code, message}]` |
| `flow.step_started` | 某步开始 | `flow_run_id, step_id, attempt, run_id` |
| `flow.step_skipped` | 条件不满足 | `flow_run_id, step_id, reason` |
| `flow.step_waiting_user` | 步骤内中断或询问用户 | `flow_run_id, step_id, kind: "interrupt" \| "failure_choice" \| "confirm"` |
| `flow.step_completed` | 某步完成 | `flow_run_id, step_id, summary, outputs, verification` |
| `flow.step_failed` | 某步一次尝试失败 | `flow_run_id, step_id, attempt, errors, next: "retry" \| "ask" \| "stop" \| "skip"` |
| `flow.finished` | 流程结束 | `flow_run_id, status, deliverables, issues, run_json_path` |

前端（T32）只依赖以上事件和 `run.json`，不解析步骤内部的工具消息来判断流程状态。会话重新连接时，通过现有会话快照接口（`session_attach`）附带当前流程的 run.json 摘要，便于恢复显示。

## 18. 结束与交付

- 直接启动的流程：控制器生成最终回复，推送为普通的最终响应。内容按 FLOW.md"交付"段组织：成果文件（含路径）、关键数量、问题清单、状态。先用模板生成；交付段要求的内容模板无法覆盖时，调用一次模型润色（输入只有 run.json 摘要和交付段）。
- 由编排智能体启动的流程：同样由控制器生成最终回复，编排智能体不再参与。
- 最终状态：全部步骤完成且没有问题为 `completed`；有审查未通过、有"失败后跳过"、有回执 issues 时为 `completed_with_issues`。

## 19. 取消、重启与继续

- 用户取消：沿用现有取消逻辑停止当前运行，流程标记 `cancelled`。
- 服务重启：启动时扫描会话中状态为 `running` 的 run.json，标记为 `interrupted`。会话打开时，流程卡片显示"流程已中断，可从第 N 步继续"。
- 继续：从中断的步骤重新执行该步（新的尝试）。因此步骤应尽量可重复执行：`layout_compose` 对同名版面执行替换，`data_load_*` 默认复用已加载图层（见 06 文档）。
- 流程级"重新运行"：用同样的输入新建一次运行。
