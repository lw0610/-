## 1. 目标

**一句话目标**：非程序员用户在前端导入或编写一份用自然语言描述的流程包，系统导入时自动体检，用户按提示修正后即可利用现有能力完成一个新的专题制图任务，整个过程不需要改代码。

为此要做到四件事：

1. 用户能看到、能理解的东西只剩三种：**工具包**（一类工具和它们的使用说明）、**流程包**（一个完整专题怎么做）、**资源**（数据清单、样式、版式、符号、参考文档）。"技能包、知识包、流程包、分类包、专属包"这些混在一起的概念全部退出用户界面。
2. 流程包用自然语言写，但系统运行时把它当成结构化的步骤来执行：一步一步交给负责的角色，检查每一步的产出，失败按规则处理。流程不再靠模型自己读一大段散文、自己记得每条"必须""禁止"。
3. 能由程序确定的事交给工具：样式、版式、数据去重加载、审查分辨率、字号锁定等不再写在提示词里让模型照做。
4. 场景知识（行军、统计、交通……）只存在于流程包和资源里；工具代码、智能体提示词、Go 代码里不再出现具体场景。

## 2. 现状问题（证据均来自当前代码）

**P1 "包"的概念混乱，一个功能要勾好几个包**
- `autocarto/skills/system` 共 87 个技能包：32 个 `category`、50 个 `workflow`、3 个 `knowledge`、2 个没写 `kind`。三种 kind 实际承担了五种职责：暴露工具、编排流程、制图规范、数据清单、审查标准。
- 前端智能体编辑抽屉（`AgentEditDrawer.tsx`）只有一个混合下拉框"智能体技能包"，三类包混在一起选。
- `workflow` 包写在 `requires_tools` 里的工具**不会**授予给智能体（`subagents/tool_config.go` 的 `LoadPackageTools` 只读取 `kind=category` 的 `tools`）。所以用一个流程包，还得另外勾上提供工具的分类包。默认方案里就有这样的漏洞：制图专家挂了 `chart-visualization`，但图表工具所在的 `misc-tools` 没有挂给任何角色，图表能力实际不可用。
- 包有四种作用域：内置、用户、全局、专属（方案独有）。

**P2 流程包是不可执行、不可校验的散文**
- 流程包通过 Eino skill 中间件按需加载正文，执行全靠模型自觉。
- 流程引用的工具在任何工具包里都没有：`print-layout-thematic` 要求调用 `layout_set_page_size`、`layout_get_item_corners`、`layout_set_map_scale`、`layout_add_file_overview`，这 4 个工具没有被任何包暴露，智能体根本看不到。
- 6 个流程包（`data-to-map-full-pipeline`、`site-suitability-analysis` 等）写的是已经不存在的角色名（`data_processing`、`vector_spatial`、`raster_terrain`、`cartography_layout`）。
- 规则互相矛盾：`data-to-map-full-pipeline` 要求"用 reproject_layer 统一坐标系"，编排提示词却禁止仅因 CRS 不同就统一。
- 同一条规则复制多份：审查 DPI"A0=100/A1=140/其他 200"出现在 4 处；四角对齐版式和字号表出现在 3 个包里（`print-layout-standard`、`print-layout-thematic`、`print-layout-marching-route`）。

**P3 场景规则写进了智能体提示词和 Go 代码**
- 默认 `agent.yaml` 里 orchestrator、cartographer、quality_feedback 的提示词有大段行军路线、统计专题、质量反馈条款。
- Go 代码按名字特判：`deepagent/agent.go` 和 `config/agent_config_manager.go` 都有 `agentName == "knowledge_engineer"`。
- 行军知识链路是约 1.4 万行的专用子系统（Go `internal/knowledge` 约 8.2K 行、Python `autocarto/knowledge` 约 4K 行、前端 `features/knowledge-review` 约 1.5K 行），而且知识编译器里还做了制图决策（红/蓝路线样式、军标 SVG 预设写在 `vocabulary.py`）。

**P4 工具里写死了制图决策**
- `layer_set_marker_symbol` 只接受 city/county，`layer_set_line_symbol` 只接受 铁路/高速公路/国道/省界/河流，`layer_set_fill_symbol` 只接受 县/市/省/河流；颜色、线宽、字号、字体都写在 `cartography_style_impl.py`（3570 行）。
- `cartography_build_and_draw_from_tables` 一个工具做五件事，并在代码里生成"国军路线名称"图层、"会师军队名称"标注。
- `layout_set_legend_style` 有 `include_military_arrow` 参数；`layout_add_file_overview` 在工具内部调大模型、按"交通/行政区"关键词套模板写综述。
- 外部插件路径、底图路径、输出目录以本机绝对路径写在技能包里；`henan_symbolization_test_flow.py`（含 `F:\qgis_project\henan-x.qgz`）放在生产代码目录。

**P5 版式靠模型按公式手算**：行军版面要求模型连续调用十几次 `layout_*` 工具，并自己按 `title_x = bx + (bw - tw) / 2` 这类公式计算位置。模型算错就再补"必须/禁止"，这是补丁循环的主要来源。

**P6 多份副本，测试钉住了提示词措辞**
- `carto_agent/defaults/skills` 是运行时不读取的旧副本（`defaults/embed.go` 不嵌入它），只有测试在读，且已与正本分叉。
- 默认方案 `agent.yaml` 有三份且内容各不相同：嵌入默认 `carto_agent/defaults/agent_configs`、开发运行副本 `autocarto_data/config/agent_configs`、只被测试读取的 `autocarto/config/agent_configs`；后者还有一份专属技能包副本 `print-layout-thematic`。
- `test_quality_feedback_review.py`、`test_scalebar_layout_contract.py`、`test_crs_reprojection_guardrails.py` 三个文件共约 130 条 `assertIn/assertNotIn`，相当一部分断言的是 SKILL.md 或 agent.yaml 的措辞；Go 侧 `default_agent_profile_test.go` 等也在断言提示词文字。改一句话就要改测试，提示词因此越改越僵。

**P7 用户写不了流程，因为看不懂工具**：311 个工具里有 32 个没有被任何工具包暴露；92 个工具的 `display_name` 就是英文函数名。

**根因**：系统里没有"一个专题"这个独立的东西。专题的数据、样式、版式、流程、审查标准无处安放，只能塞进工具代码、提示词和技能包正文。

## 3. 新的概念模型（用户只需要懂这些）

| 概念 | 是什么 | 谁维护 | 在哪里配置 |
|---|---|---|---|
| 智能体方案 | 一组角色加上启用的流程包 | 用户 | 设置 → 智能体方案 |
| 角色 | 一个子智能体：职责说明、模型、勾选的工具包。类型分"通用智能体"和"专用执行器"（如路线知识抽取） | 用户 | 方案里的角色卡片 |
| 工具包 | 一类工具（如"版面编排"）加上这类工具的使用说明和参考资料 | 系统（开发者） | 角色只能勾工具包 |
| 流程包 | 一个完整专题怎么做：适用场景、需要准备、步骤（每步谁负责、做什么、做到什么程度）、必须遵守、交付；可附带资源 | 用户 | 流程中心导入/编写；方案里勾选启用 |
| 资源 | 数据清单、样式（.qml）、版式（.qpt 或内置版式）、符号、参考文档 | 用户或系统 | 流程包自带，或放公共资源库 |

三条硬规则：
1. 角色只勾**工具包**；流程包不挂到角色上，而是在方案层启用。
2. 流程包里只写自然语言，不写函数名；系统负责把每一步匹配到具体能力并在导入时体检。
3. 场景知识只能出现在流程包和资源里。

## 4. 总体架构与运行方式

```text
用户编写/导入 FLOW.md（自然语言）+ resources/
        │
        ▼
解析（确定性：分节、步骤、字段、资源引用、角色名）
        │
        ▼
编译（模型辅助，输出受约束：每步建议能力、产出类型、条件规则、输入类型）
        │
        ▼
执行计划 flow-plan/v1 + 体检报告  ──►  前端预览：步骤卡片、错误/警告、一键修复
        │
        ▼
运行：流程执行器（FlowRunner）逐步执行
   ├─ 为本步骤组装"步骤消息"：本步做法 + 必须遵守 + 资源实际路径 + 前序产出原样 JSON + 完成标准 + 回执格式
   ├─ 交给负责角色（干净上下文，只做这一步），角色用自己工具包里的工具完成
   ├─ 读取回执 → 程序校验产出（图层/版面/文件/数据集/审查结果是否真实存在、结构是否合法）
   ├─ 失败：带原因重试一次 → 仍失败则请用户选择（重试/跳过/终止）
   └─ 写运行记录 run.json，向前端推送步骤进度事件
        │
        ▼
交付：成果文件 + 运行记录 + 问题清单
```

设计原则：
- **自然语言写，结构化跑**：用户写的是说明书，系统执行的是解析后的步骤。
- **确定的事交给工具**：一次调用完成版面排版（`layout_compose`）、按样式集批量上样式（`style_set_apply`）、按清单加载并去重（`data_load_list`）、审查导出自动选 DPI、字号锁定由工具拒绝修改。
- **每一步一个干净上下文**：步骤之间由程序原样传递产出，不再靠编排模型转述，也就不再需要"原样传递、禁止改写"这类规则。
- **导入即体检**：角色不存在、工具包没勾、资源缺失、找不到能力，在运行之前就报出来。
- **没有命中流程时照常工作**：编排智能体仍然可以按角色职责自由委派，流程只是更可靠的快捷方式。

## 6. 整体验收标准

全部满足才算重构完成：

1. **A1 旧场景不退化**：行军路线图、统计专题图以内置流程包形式运行；在固定输入下，版面快照与黄金样例一致（元素齐全，位置误差 ≤ 1 mm，图层与图例条目一致）。
2. **A2 新场景零代码**：只写 FLOW.md 和资源，完成两份新流程并成功出图——"省级人口密度分级设色图"和"考察路线图"（非军事路线，使用路线专题工具）。全程不改任何代码。
3. **A3 界面**：智能体方案页的角色只能勾选工具包；流程中心可以导入、编辑、预览、体检、导出流程包；对话页可以选择流程、填写输入、查看逐步进度。
4. **A4 去场景化**：场景词守卫测试零违规；默认方案提示词中不出现任何具体场景名。
5. **A5 质量门禁**：`./build.sh check`（go vet、go test、前端 lint 与单测、Python pytest）全部通过。

## 7. 全局执行约束（所有执行智能体必须遵守）

1. **一次只做一张任务卡**。只改任务卡"涉及范围"里的文件；发现需要改范围外的文件，先在验证记录里说明原因。
2. **不破坏用户数据**：不得修改或删除 `autocarto_data/` 下的用户数据和配置。只有 T51 可以迁移开发运行配置，且必须先备份。
3. **兼容层要登记**：保留旧接口作为过渡时，在 `carto_agent/defaults/architecture/removal_ledger.yaml` 按现有格式登记（写明删除条件和阻塞测试），并保证 `go test ./internal/control -run TestCompatLayerRequiresRemovalCriteria` 通过。
4. **测试测行为，不测措辞**：新测试不得断言提示词、SKILL.md、FLOW.md 的具体文字。可以断言结构（字段、步骤数、工具归属、解析结果、诊断码）和工具行为。
5. **工具代码不得出现场景词**：工具实现、Go 运行时、默认提示词中不得出现"行军、河南、军标、国军、红军、敌军、会师、China_map"、本机绝对路径和外部插件目录字面量（守卫测试见 T03）。
6. **用户可见文案用中文**，代码标识符、文件名中的固定字段用英文。
7. **每张任务卡完成后**，在 `docs/refactor/evidence/Txx.md` 写验证记录：改了什么、运行了哪些命令、结果、遗留问题。
8. **以代码事实为准**：本方案与代码现状不一致时，以代码为准实现目标，并在验证记录里写明差异。
9. **质量门禁**：提交前至少运行任务卡列出的测试命令；涉及多个子系统时运行 `./build.sh check`。

## 8. 交给执行智能体时的提示词

```text
你是本仓库的执行智能体，请完成任务 Txx。
```

## 9. 术语表

| 术语 | 含义 |
|---|---|
| 工具 / 能力 | 一个可调用的 QGIS 或内部操作，如"加载矢量图层"。面向用户叫"能力"，用中文名展示 |
| 工具包 | `kind: category` 的 SKILL.md：一组工具和它们的使用说明、参考资料 |
| 系统基础包 | 自动挂给所有角色、不出现在勾选列表的工具包（工程状态、运行控制） |
| 隐藏包 | 用户不能勾选、由系统按 `auto_mount` 自动挂载的工具包（如流程控制、能力查询、路线知识） |
| 流程包 | 一个目录：`FLOW.md` + 可选 `resources/` |
| 执行计划 | 流程包编译后的结构化结果 `flow-plan/v1`（内部 JSON，用户看到的是预览） |
| 体检 | 编译时的检查，结果是诊断列表（错误/警告/提示） |
| 流程执行器 | FlowRunner，按执行计划逐步推进的控制器；每一步是一次独立的智能体运行 |
| 回执 | 每一步结束时负责角色输出的 JSON：状态、产出、问题 |
| 运行记录 | `run.json`，记录一次流程运行的输入、每步状态、回执、校验结果 |
| 专用执行器 | 不是通用对话智能体、而是专用程序的角色，如路线知识抽取 |
| 黄金样例 | 固定输入加上基线成果，用于判断重构有没有改坏 |
