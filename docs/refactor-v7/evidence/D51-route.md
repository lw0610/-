## 实际发现：失败回执丢失部分成功明细

环境可用后，真实 28 条路线中 27 条可绘制，1 条被插件拒绝：`同一贝塞尔段出现回环，无法作为稳定的路线带`。Python 回执已含逐条 route_id、成功图层 ID 和失败原因，Go 却只把总提示 `部分路线绘制失败` 交给模型。模型因看不到具体路线反复读取资源和重绘，内容修复没有足够信息。

修正后的失败通路保持失败状态与原校验：`ToolInvokeError.Output` 保存原结构化回执，错误映射器只在 `output` 字段传递一份；错误字符串仍是简短摘要，不拼接大段日志。真实成功路线和失败路线的信息都能到模型。针对两条路线一成功一失败的回归验证了成功 layer_id、失败 route_id 和具体原因均保留、没有重复放进 error 字符串。

验证：`go test ./cmd/agent ./internal/agentruntime ./internal/capability -run 'TestQGISPartialFailure|TestWrapToolWithErrorHandler|TestDefaultError' -count=1` 通过。

真实继续执行后，已在模型工具回执中看到逐路线结构，模型正确报告 27 条成功和第一阶段主线 1 条失败。此前模型一度把整批写成 28 条成功，说明保留工具明细具有实际作用。仍不能据部分图层生成宣称完整制图成功。

## 实际发现：核验读取了错误的 JSON 层级

重规划把路线产出几何改为 `polygon`（渲染器实际输出 MultiPolygon），后续却仍收到“图层几何与声明不符”。核查真实工具契约：`layer_inspect` 返回 `{success:true,data:{geometry,...}}`；`verify_outputs.go` 调用的 `UnwrapToolResult` 只解 `output`/`result`，随后错误地在顶层取 `geometry`，实际得到空值。固定工具夹具的元数据放在顶层，没有暴露这个集成错误。

该问题交主代理按真实 `layer_inspect` 契约修正，也须核对 `extent.from` 对同一工具结果的读取。不能把这次错误提示当作用户需要确认的地理数据问题。

已修 `verify_outputs.go` 与 `plan_acquisition_v2.go` 两处，分别读取 `data` 内的几何/字段与范围；没有改通用 `UnwrapToolResult`。新增真实嵌套回执的成功检查、真实缺字段/几何错误仍拒绝、memory 图层范围提取回归。`go test ./internal/flowrun ./internal/websocket -run '^TestV7(VerifyLayer|MemoryExtent)' -count=1` 通过。

## 第一阶段主线的几何原因

核对 `route_paths.csv` 的 18 个点与史料顺序一致，适配器没有打乱顺序或拼入敌方支线。实际坐标依次从何家冲、朱堂、东双河到桐柏、枣阳，再掉头至保安寨、界碑口，最终经泌阳等处抵达独树镇。

只读导入外置渲染器的原算法诊断（没有改插件或数据）：相同 18 个点经相同局部米制变换，在 5,000 米带宽下，第 7 段“桐柏→枣阳”（端点距离约 67,814 米）拟合出单段回环；1,000 米及 100 米带宽下没有单段回环。输入折线本身存在交叉；外置算法允许真实行军回返，但明确拒绝单条三次贝塞尔曲线内自交。这说明故障与曲线拟合、点间距和宽度有关，不能归咎于本项目误排序，也不能靠跳过主线宣称成功。

当前第一项停在真实交互检查点，没有最终 PDF。最后一轮 257.55 秒、26 次工具调用；已修结构化回执丢失，但核验封装修复之后尚未再跑。回放发出的“几何为 MultiPolygon 是否接受”来自错误核验，不应让用户承担代码错误的确认。
