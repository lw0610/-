# R31 绑定迁移与单一绑定存储

## 结论
完成。生产启动、API 惰性装配和离线验收共享同一个注入的 `*bindings.Store`。旧绑定在读取时仅做内存迁移，首次保存时备份原始文件再原子写入 v2。迁移样例、绑定写入和备份断言均使用临时目录。后续发现外层 shell 保留旧 Eino 环境变量，已显式覆盖 enio2 的 project/assets 和 `/tmp/enio2-r40-go-home` 后重跑绑定范围全部测试，结果通过（`/tmp/enio2-r31-isolated-recheck.log`）；后续命令统一显式隔离环境。

## 改动摘要
- 新绑定键使用资源编号、流程内 `resources/` 相对路径、或 `library:<资源编号>`；不再使用声明类型与标签的哈希。资源显示名称变化不丢失绑定。
- `resource-bindings/v2` 持久化 `bindings` 和 `orphaned`；旧公共名称必须对应唯一数据清单，旧流程哈希按当前声明映射，歧义、未知键及映射后值冲突均保留原始记录。
- 项目内目录保存相对路径，项目外目录保存绝对路径；旧 `../数据/...` 按项目根解析。迁移不要求外部数据当前在线。
- 备份保存在绑定配置旁的 `backups/resource_bindings-<时间戳>-<唯一后缀>.yaml`，内容与原文件逐字节一致；备份失败不改原文件，v2 再次读取不重迁移或增加 v1 备份。
- 公共共享绑定作为流程绑定的回退，但返回的 `binding_key` 始终保持当前流程作用域，用户为当前流程重新选目录不会误改所有流程的共享目录。
- `NewDefaultStore(library)` 统一生产构造与迁移准备；主程序、API fallback、acceptance 使用该构造函数。旧 hash 函数只存在于 v1 迁移文件。
- 独立 `GET /api/flows/bindings/status` 返回 `orphaned_count`，注册于流程 ID 路由前，空流程列表也能提示迁移遗留记录。
- 成功解析只接受资源自身身份生成稳定 key；未解析的资源保留 `unresolved:<type>:<label>` 诊断引用，供 R50 定位待修复声明，绑定接口不接受此类键。
- 新登记兼容层 `resource_bindings_v1_reader`；删除窗口为自动迁移发布两个版本之后。

## 与方案不一致之处
- 顶部孤立提示使用独立状态接口，避免每条流程摘要重复计数并兼容空列表；已与 R61 前端约定。
- 启动只准备/验证内存迁移，首次成功保存才备份落盘，遵循 01 §7.3；不主动重写用户旧文件。
- 旧式公共数据清单暂用规范推断的 `legacy.data_list.<hash10>` 编号绑定；键校验显式接受这类兼容编号，升级正式编号后的迁移由 R50/R51处理。

## 涉及范围以外的必要修改
- `resource/handle.go`、`resource/types.go`、`resource/resolver.go`：绑定查找必须在读取清单前拿到稳定资源身份；移除临时旧 hash 生成。
- 两份 acceptance 场景 JSON 与三份编译计划快照同步稳定键。
- `tmp/t51/main.go` 已由 G5 移除，本卡不重复处理。
