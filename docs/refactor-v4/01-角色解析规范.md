# 01 角色解析规范

## 1. 原则

1. **流程声明需求，方案提供成员**。流程写“需要一个什么样的执行者”（职责、工具包、执行器、模型要求）；方案决定由谁来做。两者通过确定性的“角色解析”连接，结果写进执行计划，界面可见、可改。
2. **补齐优先于阻断**。方案没有合适角色或角色缺工具包时，按方案策略临时补齐；只有补不齐、且本次一定执行的步骤才阻止运行。
3. **不改用户方案**。合成角色和临时补齐只存在于内存与 `run.json` 计划快照；方案文件只在用户主动保存“角色对应”或策略时改变。
4. **请求路径不调模型**。解析、补齐、可达性判断全部是确定性计算。

## 2. FLOW.md 语法

### 2.1 参与角色

新增一级章节 `## 参与角色`（别名：`角色分工`、`需要的角色`）。每个角色一个三级标题，字段写法与步骤字段相同：

```markdown
## 参与角色

### 数据工程专家
- 职责：数据接入、核验与必要转换
- 工具包：数据加载与导出、坐标系、格式转换

### 质量反馈智能体
- 职责：读取导出图片做版面审查
- 工具包：质量审查
- 模型：读图

### 制图知识抽取专家
- 执行器：路线知识抽取
```

| 字段 | 别名 | 必需 | 含义 |
|---|---|---|---|
| 职责 | 说明、描述 | 建议 | 一句话职责；流程自带角色把它作为角色说明 |
| 工具包 | 能力 | 通用角色建议 | 顿号分隔；接受工具包编号、显示名，或去掉括号部分的显示名（`遥感影像` 匹配 `遥感影像（GEE）`） |
| 执行器 | — | 执行器角色必需 | 专用执行器显示名或类型（`路线知识抽取` / `route_knowledge`）；与“工具包”互斥 |
| 模型 | — | 否 | 目前只支持 `读图`：需要能接收图片的模型 |
| 只用方案角色 | — | 否 | 写“是”时本角色不使用流程自带角色补位（方案策略为 `strict` 时所有角色都如此） |

用三级标题而不是 `名称（属性）：说明`，是因为工具包显示名本身含括号（如 `遥感影像（GEE）`），放进属性括号会嵌套。

### 2.2 步骤字段

| 字段 | 别名 | 含义 |
|---|---|---|
| 负责 | 不变 | 优先匹配本流程参与角色名称；不在参与角色中时按旧规则直接匹配方案角色（§8） |
| 能力 | 需要能力 | 本步除角色工具包外额外需要的工具包；`能力：A、B；可选：C`，分号后的“可选：”只在可用时授予，缺失不影响运行 |

数据获取不再由步骤字段表达，改由 `## 数据需求` 声明（`02` §3）；系统获取执行器是系统自带的执行器，不需要方案中有对应角色（`03` §1）。流程作者确需自定义获取步骤时，用数据需求的“获取方式：「第N步」”指向一个普通步骤，该步骤按本规范解析角色。

解析期诊断（不依赖方案）：

| 诊断码 | 级别 | 条件 |
|---|---|---|
| `FLOW_ROLE_SLOT_DUPLICATE` | 错误 | 参与角色名称重复 |
| `FLOW_ROLE_SLOT_INVALID` | 错误 | 同时写了“执行器”和“工具包”，或执行器类型未注册 |
| `FLOW_ROLE_SLOT_FIELD_UNKNOWN` | 警告 | 参与角色中出现未知字段 |
| `FLOW_ROLE_SLOT_UNUSED` | 提示 | 声明了但没有步骤使用 |
| `FLOW_ROLE_SLOT_UNDECLARED` | 警告 | 流程有参与角色章节，但某步“负责”不在其中（按旧规则处理） |

## 3. 工具包名称规范化

计划阶段（`internal/flow`，环境中已有 `Packages`）把原文写法转换为工具包编号：

1. 与编号完全相同；
2. 与显示名完全相同；
3. 去掉显示名中的 `（…）` / `(...)` 后完全相同；
4. 以上任一步匹配到多个时报 `FLOW_ROLE_PACKAGE_AMBIGUOUS`（错误）；都不匹配时报 `FLOW_ROLE_PACKAGE_UNKNOWN`（级别按可达性，§6）。

**可授予工具包**：存在于正式目录、已启用、`kind: category`、非隐藏、不在受限清单中。受限清单为代码常量 `restrictedFlowPackages = {"pyqgis-scripting", "creator-tools"}`（README §8 第 3 项可调整），由 F50 守卫测试固定。

## 4. 解析算法

### 4.1 输入

- 执行计划环境 `flow.Environment`（`internal/api/flow_environment.go`）：角色列表（已含共享包和自动挂载包的实际工具包）、工具包目录、启用流程。
- 新增：方案策略 `RoleFill`（`auto` | `flow_role` | `strict`，空值按 `auto`）、方案映射 `RoleMapping[flowID][slot]`、主角色模型名、可读图模型列表（§7.2）。

### 4.2 通用角色位

对每个参与角色（非执行器）按顺序尝试，命中即停：

| 顺序 | 来源 `source` | 条件 |
|---|---|---|
| 1 | `mapping` | 映射值是方案角色编号，该角色存在、已启用、`kind: agent`。映射值为 `flow_role` 时直接跳到第 4 步。映射失效时记 `FLOW_ROLE_MAPPING_INVALID`（警告）并继续 |
| 2 | `scheme_name` | 显示名或编号与角色位名称**完全相同**，已启用，`kind: agent` |
| 3 | `scheme_capability` | 仅当角色位声明了工具包：已启用、`kind: agent`、非主角色，且实际工具包**包含**全部所需工具包；多个时取多余工具包最少者，再按方案角色现有顺序 |
| 4 | `flow_role` | 策略不是 `strict`、角色位未写“只用方案角色”、所需工具包全部可授予、模型要求可满足时，合成流程自带角色 |
| — | `unresolved` | 以上都不满足；记录原因 |

第 1、2 步命中、但该角色缺少角色位所需工具包时：

- `auto`：保留该角色，缺少的工具包作为“临时补齐”（`granted`）。缺少的工具包里有不可授予的项时，该角色位视为未解析（原因 `FLOW_ROLE_PACKAGE_RESTRICTED`）。
- `flow_role`：放弃该角色，继续第 3、4 步。
- `strict`：保留该角色，记 `FLOW_CAPABILITY_MISSING_IN_ROLE`（沿用现有诊断码，修复动作 `add_tool_package`），级别按可达性。

被禁用的方案角色视同不存在（README §8 第 2 项）；预览中注明“方案中的同名角色已禁用”。

### 4.3 执行器角色位

| 顺序 | 来源 | 条件 |
|---|---|---|
| 1 | `mapping` | 映射到 `kind: executor` 且执行器类型相同、已启用的角色 |
| 2 | `scheme_executor` | 方案中任一已启用、执行器类型相同的角色；多个时优先同名，再按顺序 |
| 3 | `executor_default` | 策略不是 `strict` 时，使用系统内置配置合成执行器角色，模型为主角色模型 |
| — | `unresolved` | 原因 `FLOW_EXECUTOR_ROLE_MISSING` |

执行器所需输入与资源的现有检查（`internal/flow/executors.go`、`diagnose.go` 中 `FLOW_EXECUTOR_INPUT_MISSING`）不变。

### 4.4 每一步的最终绑定

```text
所需工具包(step) = 角色位工具包 ∪ 步骤“能力”必需项
缺少(step)       = 所需工具包(step) − 绑定角色的实际工具包（流程自带角色按其声明计）
```

- 缺少为空：直接使用角色位的解析结果。
- `auto`：缺少项全部可授予 → 本步 `granted` 增加这些项；否则本步未解析（`FLOW_ROLE_PACKAGE_RESTRICTED` 或 `FLOW_ROLE_PACKAGE_UNKNOWN`）。
- `flow_role`：本步改用该角色位的流程自带角色，并带上本步所需工具包；不能合成时未解析。
- `strict`：`FLOW_CAPABILITY_MISSING_IN_ROLE`。
- “可选：”工具包：可授予且（如果依赖扩展服务）已就绪时加入 `granted`；否则只记提示，不影响绑定。

同一角色位的各步通常得到同一个绑定；只有步骤“能力”不同才可能出现差异，预览按步骤显示。

### 4.5 读图要求

- 绑定到方案角色（映射、同名、工具包匹配、方案执行器）时不检查模型：用户已为该角色选择模型。
- 合成流程自带角色时：优先主角色模型（若标记“支持读图”），否则取模型配置中第一个标记“支持读图”的模型；都没有时未解析，原因 `FLOW_ROLE_VISION_UNAVAILABLE`。

## 5. 执行计划中的结构（`internal/flow/plan.go`）

```go
type RoleSlotPlan struct {
	Name        string         `json:"name"`
	Description string         `json:"description,omitempty"`
	Packages    []string       `json:"packages"` // 工具包编号
	Executor    string         `json:"executor,omitempty"`
	NeedsVision bool           `json:"needs_vision,omitempty"`
	Resolution  RoleResolution `json:"resolution"`
}

type RoleResolution struct {
	Source    string   `json:"source"` // mapping|scheme_name|scheme_capability|scheme_executor|flow_role|executor_default|unresolved
	RoleID    string   `json:"role_id,omitempty"`
	RoleLabel string   `json:"role_label,omitempty"`
	Granted   []string `json:"granted"` // 角色位级临时补齐
	Reason    string   `json:"reason,omitempty"`
	Note      string   `json:"note,omitempty"` // 例如“方案中的同名角色已禁用”
}

// 合成角色定义，随计划进入 run.json，恢复时原样使用。
type FlowRoleSpec struct {
	ID           string   `json:"id"`   // flow_role_<sha256(flowID+"\x00"+slot) 前 12 位十六进制>
	Slot         string   `json:"slot"`
	DisplayName  string   `json:"display_name"`
	Description  string   `json:"description,omitempty"`
	Kind         string   `json:"kind"` // agent | executor
	Executor     string   `json:"executor,omitempty"`
	ToolPackages []string `json:"tool_packages"`
	Provider     string   `json:"provider,omitempty"` // 模型配置名，空表示主角色模型
}

// FlowPlan 新增
RoleSlots []RoleSlotPlan `json:"role_slots"`
FlowRoles []FlowRoleSpec `json:"flow_roles"`

// StepPlan 新增
RoleSlot        string   `json:"role_slot,omitempty"`
RoleSource      string   `json:"role_source,omitempty"`
RequiredPackages []string `json:"required_packages"`
GrantedPackages  []string `json:"granted_packages"`   // 本步临时补齐（含角色位级）
Unresolved       string   `json:"unresolved,omitempty"` // 未解析原因的诊断码；空表示已解析
```

`StepPlan.Role` 保存方案角色编号或合成角色编号；`Kind` 规则不变（执行器角色位为 `executor`）。`Roles []RoleSpec` 保持现有含义（方案角色快照），不放合成角色。

## 6. 可达性与诊断分级

### 6.1 可达性函数（新建 `internal/flow/reachability.go`）

```go
type Reach string // "must" | "maybe" | "never"
func StepReach(plan *FlowPlan, inputs map[string]any, modes map[string]string) map[string]Reach
```

- 无条件 → `must`。
- 条件规则只涉及输入（`provided`、`not_provided`、`truthy`、`falsy`、`equals` 及其 `and`/`or`/`not` 组合）→ 按输入求值。来源方式为 `auto`、`fill` 的输入视为“已提供”（获取后才有值，按乐观处理）。
- 涉及 `step_status`、`output_exists`，或条件未能转换为规则 → `maybe`；组合时按三值逻辑。
- 隐式获取步骤（`03` §2）与“获取方式：「第N步」”指向的自定义获取步骤：其绑定的输入都不需要获取（来源方式为 `user` 或 `none`）→ `never`；否则 `must`，自定义步骤再与自身条件组合。
- `inputs == nil`（只看流程，不看本次输入）时：有条件的步骤一律 `maybe`。

`provided`/`truthy` 的判定从 `internal/flowrun/inputs.go` 移到 `internal/flow`（导出为 `InputProvided`、`InputTruthy`），`flowrun` 改为调用它们，保证预判与运行时语义一致。

### 6.2 三个检查点

| 检查点 | 输入 | 未解析的步骤 |
|---|---|---|
| 执行计划（打开、保存、列表、`AvailablePlans`） | 不看输入 | `must` → 错误（阻止运行）；`maybe` → 警告，消息附“仅在条件满足时需要：<条件原文>” |
| 输入校验与运行开始（`inputs/check`、`preparePlan`） | 本次输入和来源方式 | `must` → 阻止，`StartupIssue` 写明步骤与原因；`maybe` → 提示 |
| 运行到该步（`advance`） | 条件已求值为真 | 不调用角色；本次尝试记为失败（原因同上），直接进入“询问用户”（不自动重试），可选择跳过或停止 |

`StartupIssue` 增加 `Step string \`json:"step,omitempty"\``。`AvailablePlans` 只排除有错误的流程，因此只有条件步骤缺执行者的流程仍会出现在编排智能体的可用流程中。

## 8. 方案配置与模型配置

### 8.1 方案（`internal/config/agent_config_manager.go`）

新增顶层块 `flow_policy`，**不放进现有 `flows`**：`flows` 为非空且 `enabled` 缺失时表示“全部禁用”（`flow_environment.go` 中 `profile.Flows != nil` 的分支），把策略塞进去会让只设置了策略的方案意外禁用全部流程。

```yaml
flow_policy:
  role_fill: auto        # auto（默认）| flow_role | strict
  auto_acquire: ask      # ask（默认）| allow | deny，见 04 §7
  role_mapping:
    traffic-route:
      空间分析专家: spatial_analyst   # 或 flow_role
```

```go
type FlowPolicyConfig struct {
	RoleFill    string                       `yaml:"role_fill,omitempty" json:"role_fill,omitempty"`
	AutoAcquire string                       `yaml:"auto_acquire,omitempty" json:"auto_acquire,omitempty"`
	RoleMapping map[string]map[string]string `yaml:"role_mapping,omitempty" json:"role_mapping,omitempty"`
}
// AgentConfigFile 新增
FlowPolicy *FlowPolicyConfig `yaml:"flow_policy,omitempty" json:"flow_policy,omitempty"`
```

- 校验：枚举值非法时拒绝保存；映射到不存在的角色允许保存（计划中给 `FLOW_ROLE_MAPPING_INVALID`）。
- `settings.ExpandAgentProfileView` 必须包含该块，使 `SchemeRevision` 随策略和映射变化。
- 迁移、复制方案、导入导出方案时原样保留；前端方案类型同步。

### 8.2 模型（`internal/config/config.go` `LLMProviderConfig`）

新增 `Vision bool \`yaml:"vision"\``（界面文案“支持读图”），配置读写接口、前端模型设置同步。它只用于为流程自带角色选模型，不改变现有角色的模型行为。

## 9. 兼容

1. **没有参与角色章节的流程**：每个不同的“负责”原文视为一个隐式角色位（无工具包）。只走 §4.2 第 1 步（按原文映射）和旧匹配规则（显示名精确 → 编号 → 显示名包含，多匹配报 `FLOW_ROLE_AMBIGUOUS`），可以匹配到执行器角色；不走工具包匹配和流程自带角色。诊断码沿用 `FLOW_ROLE_NOT_FOUND`、`FLOW_ROLE_DISABLED`、`FLOW_ROLE_AMBIGUOUS`，级别按 §6。步骤若写了“能力”，同样按 §4.4 补齐。
2. **“用户/人工”**仍为人工确认步骤；**“系统自动”或留空**仍为 `kind=auto`，本轮不改选角规则（见 `05` “不在本轮”）。
3. **旧 `run.json`**：没有 `flow_roles`、`granted_packages` 时按原逻辑恢复。
4. **旧版本程序读新流程**：`## 参与角色` 按未知章节进入备注；未知步骤字段的处理由 F10 实测并写入验证记录。内置流程改写后版本号升为 `3.0.0`。

| `FLOW_ROLE_PACKAGE_AMBIGUOUS` | 错误 | 工具包名称匹配多个 | — |
| `FLOW_ROLE_PACKAGE_RESTRICTED` | 按可达性 | 所需工具包受限，不能补齐 | `map_role` |
| `FLOW_ROLE_MAPPING_INVALID` | 警告 | 映射的角色不存在或已禁用 | `map_role` |
| `FLOW_ROLE_AUGMENTED` | 提示 | 将为方案角色临时补齐工具包 | `add_tool_package`（改为永久） |
| `FLOW_ROLE_FLOW_ROLE` | 提示 | 使用流程自带角色 | `map_role` |
| `FLOW_ROLE_EXECUTOR_DEFAULT` | 提示 | 使用系统默认执行器 | — |
| `FLOW_ROLE_VISION_UNAVAILABLE` | 按可达性 | 没有支持读图的模型 | `open_models` |
| `FLOW_EXECUTOR_ROLE_MISSING` | 按可达性 | `strict` 下方案没有对应执行器角色 | `open_scheme` |
| `FLOW_ROLE_NOT_FOUND` / `FLOW_ROLE_DISABLED` / `FLOW_ROLE_AMBIGUOUS` | 按可达性（歧义为错误） | 旧写法流程 | `set_role` / `enable_role` / `map_role` |
| `FLOW_CAPABILITY_MISSING_IN_ROLE` | 按可达性 | `strict` 下角色缺工具包 | `add_tool_package` |

“按可达性”指 §6.2：`must` 为错误，`maybe` 为警告。新增修复动作 `map_role`（打开角色对应页）、`open_models`（打开模型设置），前端需识别。
